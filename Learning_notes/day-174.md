# 2. What Is Inference?

Inference is the process of using a trained machine learning model to make predictions or generate outputs from new input data.

In Large Language Models (LLMs), inference means giving the model a prompt and asking it to generate a response.

Example:

**Input:**

```text
Explain artificial intelligence in simple words.
```

**Model Output:**

```text
Artificial intelligence is technology that allows computers
to perform tasks that normally require human intelligence.
```

The model uses the knowledge and patterns it learned during training to generate the response.

### Important

Training changes the model's trainable parameters.

Inference uses the already-trained parameters to generate outputs.

Inference does not normally update model weights.

# 3. Training vs Inference

| Training | Inference |
|---|---|
| Model learns from training data. | Model generates responses from input. |
| Updates trainable parameters. | Does not update model parameters. |
| Requires a training dataset. | Requires an input prompt. |
| Can require significant GPU resources. | Resource requirements depend on model size and workload. |
| Example: LoRA fine-tuning. | Example: Asking a fine-tuned model a question. |

Example workflow:

```text
Training Data
     |
     v

     |
     v

     |
     v

     |
     v
Save Adapter
     |
     v

     |

     |
     v
Generated Response
```

# 4. What Is a LoRA Adapter?

LoRA stands for Low-Rank Adaptation.

It is a Parameter-Efficient Fine-Tuning (PEFT) technique.

Instead of updating all original model parameters, LoRA introduces smaller trainable matrices into selected layers.

During training:

- Original model weights are generally frozen.
- LoRA parameters are trained.
- The adapter learns task-specific adjustments.

After training, the adapter can be saved separately.

For our project:

**Base Model:**

`Qwen/Qwen2.5-0.5B`

**Fine-Tuned Model:**

`Qwen/Qwen2.5-0.5B + LoRA Adapter`

# 5. Loading a Saved LoRA Adapter

We previously saved our adapter on Day 173.

Now we can load it without repeating training.

We need:

1. Original base model.
2. Saved LoRA adapter.
3. Compatible tokenizer.

Example:

```python
import torch

from transformers import AutoTokenizer, AutoModelForCausalLM
from peft import PeftModel

BASE_MODEL = "Qwen/Qwen2.5-0.5B"

ADAPTER_PATH = "./day173-lora-adapter"

# Load tokenizer
tokenizer = AutoTokenizer.from_pretrained(BASE_MODEL)

# Load original base model
base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    torch_dtype="auto",
    device_map="auto"
)

# Attach the trained LoRA adapter
model = PeftModel.from_pretrained(
    base_model,
    ADAPTER_PATH
)

model.eval()

print("Fine-tuned model loaded successfully!")
```

### Understanding the Code

**AutoTokenizer.from_pretrained()**

Loads the tokenizer associated with the model.

**AutoModelForCausalLM.from_pretrained()**

Loads the original pretrained language model.

**PeftModel.from_pretrained()**

Loads the saved LoRA adapter and attaches it to the base model.

**model.eval()**

Places the model in evaluation mode.

This disables training-specific behaviours such as dropout during inference.

# 6. Running Inference with the Adapter

After loading the model, we can generate responses.

Example:

```python
prompt = "Explain machine learning in simple words."

inputs = tokenizer(
    prompt,
    return_tensors="pt"
).to(model.device)

with torch.inference_mode():

    outputs = model.generate(
        **inputs,
        max_new_tokens=100,
        temperature=0.7,
        do_sample=True,
        pad_token_id=tokenizer.eos_token_id
    )

response = tokenizer.decode(
    outputs[0][inputs["input_ids"].shape[1]:],
    skip_special_tokens=True
)

print("Question:", prompt)
print("Response:", response)
```

### Understanding the Code

**1. Create a prompt**

```python
prompt = "Explain machine learning in simple words."
```

This is the input given to the model.

**2. Tokenize the prompt**

```python
inputs = tokenizer(
    prompt,
    return_tensors="pt"
).to(model.device)
```

Converts text into token IDs that the model understands.

**3. Generate a response**

```python
outputs = model.generate(
    **inputs,
    max_new_tokens=100,
    temperature=0.7,
    do_sample=True
)
```

The model generates new tokens based on the input.

**4. Decode the output**

```python
tokenizer.decode()
```

Converts generated token IDs back into readable text.

**5. Use inference mode**

```python
with torch.inference_mode():
```

Disables gradient calculation during inference, reducing unnecessary memory usage.

# 7. Important Generation Parameters

| Parameter | Meaning |
|---|---|
| max_new_tokens | Maximum number of new tokens generated. |
| temperature | Controls randomness in token selection. |
| do_sample | Enables sampling instead of purely greedy decoding. |
| top_p | Controls nucleus sampling when enabled. |
| top_k | Restricts sampling to the top K candidate tokens. |
| pad_token_id | Specifies the padding token ID. |

### Temperature

Temperature affects how predictable or varied the generated response is.

- Lower temperature: More predictable responses.
- Higher temperature: More varied responses.

Example:

```python
temperature=0.2
```

Produces more conservative generation.

```python
temperature=0.9
```

Allows more variation.

Temperature is not a direct measure of accuracy.

# 8. What Is Adapter Merging?

Adapter merging means combining the trained LoRA adapter's weight updates with the original base model weights.

Normally, a LoRA model uses:

```text
Base Model + LoRA Adapter
```

After merging:

```text
Merged Model
```

The merged model contains the original model weights with the adapter updates incorporated.

Conceptually:

```text
Original Weights (W)
        +
LoRA Weight Updates (ΔW)
        |
        v
Merged Weights (W + ΔW)
```

The adapter no longer needs to be loaded separately for inference.

### Why Merge Adapters?

- Simplifies model deployment.
- Makes serving easier in some environments.
- Avoids separately loading the adapter at inference time.
- Produces a standalone model checkpoint.

### Important

Merging does not retrain the model.

It combines already-trained adapter updates with the base model weights.

# 9. How to Merge a LoRA Adapter

PEFT provides a method called:

`merge_and_unload()`

Example:

```python
from peft import PeftModel
from transformers import AutoModelForCausalLM

BASE_MODEL = "Qwen/Qwen2.5-0.5B"

ADAPTER_PATH = "./day173-lora-adapter"

# Load base model
base_model = AutoModelForCausalLM.from_pretrained(
    BASE_MODEL,
    torch_dtype="auto",
    device_map="auto"
)

# Load adapter
model = PeftModel.from_pretrained(
    base_model,
    ADAPTER_PATH
)

# Merge adapter into base model
merged_model = model.merge_and_unload()

# Save merged model
merged_model.save_pretrained(
    "./day174-merged-model",
    safe_serialization=True
)

print("Merged model saved successfully!")
```

### What Does merge_and_unload() Do?

1. Combines the LoRA weight updates with the original model weights.
2. Removes the separate adapter structure from the returned model.
3. Returns a regular model containing the merged weights.

**Important:** Merging may require additional memory. Quantized models can have merging restrictions or require dequantisation, depending on the configuration.

# 10. What Is Model Serving?

Model serving means making a trained model available so that applications can send inputs and receive generated outputs.

Imagine building an AI application.

A user types:

"Explain machine learning."

Your application sends the request to a model.

The model generates an answer and sends it back.

This process is called model serving.

### Basic Architecture

```text
User
 |
 v
Frontend Application
 |
 v
Backend API
 |
 v
Model Server
 |
 v
Fine-Tuned LLM
 |
 v
Generated Response
 |
 v
Frontend Application
```

# 11. Common Model Serving Tools

| Tool | Purpose |
|---|---|
| Hugging Face Transformers | Loads models and performs inference. |
| Hugging Face PEFT | Loads and manages LoRA adapters. |
| vLLM | High-throughput LLM inference and serving. |
| Ollama | Runs and manages local language models. |
| FastAPI | Builds HTTP APIs using Python. |
| Hugging Face TGI | Serves language models through an inference server. |

Different tools suit different deployment requirements.

For example:

- Transformers is useful for learning and experimentation.
- vLLM is designed for efficient LLM serving.
- FastAPI can expose model functionality through an API.
- Ollama is useful for running supported models locally.

# 12. Inference vs Serving

These concepts are related but different.

| Inference | Serving |
|---|---|
| Generates a model output. | Makes model inference accessible to applications. |
| Can happen inside a Python script. | Usually exposes a service or endpoint. |
| Processes a prompt. | Receives requests and returns responses. |
| Example: `model.generate()` | Example: A FastAPI endpoint. |

Inference is the model operation.

Serving is the system that makes that operation available.

# 13. Common Mistakes During Inference

### Mistake 1: Forgetting the Base Model

A LoRA adapter normally needs its compatible base model.

### Mistake 2: Loading the Wrong Adapter

The adapter must correspond to the intended base model and training configuration.

### Mistake 3: Forgetting Evaluation Mode

Use:

```python
model.eval()
```

This disables training-specific behaviours such as dropout.

### Mistake 4: Forgetting Inference Mode

Use:

```python
with torch.inference_mode():
```

This avoids unnecessary gradient calculations.

### Mistake 5: Incorrect Tokenizer

Use a tokenizer compatible with the base model and training setup.

### Mistake 6: Incorrect Prompt Format

Some instruction-tuned models expect a specific chat template.

Using the wrong format can reduce response quality.

### Mistake 7: Expecting Training to Happen During Inference

Inference does not train the model.

It only uses the existing trained parameters to generate responses.
