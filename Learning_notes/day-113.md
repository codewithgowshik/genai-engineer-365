# Day 113 — Build a Minimal RAG Pipeline

## Objective

Today marks the beginning of Phase 4: Retrieval-Augmented Generation (RAG). The goal is to understand what RAG is, why it matters, and how it extends the semantic search system built in Project 3.

The main idea is simple: instead of asking an LLM to answer a question using only what it already knows, we first retrieve relevant information from our own data and then provide that information to the LLM as context.

---

## 1. What is RAG?

RAG stands for Retrieval-Augmented Generation. It combines two important steps: retrieval and generation.

The retrieval step finds relevant information from a collection of documents. The generation step gives that retrieved information to an LLM along with the user's question so that the model can generate an answer using the provided context.

The basic RAG flow is:

```text
User Question
      ↓
Retrieve Relevant Documents
      ↓
Retrieved Context
      ↓
LLM + Context
      ↓
Generated Answer
```

The key idea is that the LLM does not have to rely only on information contained in its original training. Relevant information can be retrieved from an external data source and supplied at question time.

---

## 2. Why RAG Matters

An LLM may not know the contents of a private document, company knowledge base, university notes, product documentation, or a custom dataset. RAG provides a way to retrieve relevant information from that data and use it when generating an answer.

For example, if a user asks what a document says about vector databases, the system can first find the relevant document or document chunk. That information can then be included in the prompt sent to the LLM.

The important distinction is:

> Retrieval finds the information. Generation turns that information into an answer.

## 3. Connection to Project 3

Project 3 focused primarily on retrieval. The Semantic Search Engine converted documents and queries into embeddings, stored document embeddings in Chroma, and retrieved relevant documents using similarity search.

The Project 3 flow was approximately:

```text
Query
  ↓
```

RAG adds a generation stage after retrieval:

```text

  ↓

  ↓

  ↓

```

This means Phase 4 is building directly on the work completed in Project 3 rather than starting from zero.

## 5. Building the Context

After retrieving the documents, the documents need to be combined into a single piece of context that can be included in the LLM prompt.

The basic idea is:

```python
results = search(query, k=3)
documents = results["documents"][0]
context = "\\n\\n".join(documents)
```

The retrieved documents now form the context for the generation step.

For example, the context might contain information such as:

```text
Machine learning allows computers to learn patterns from data.

Artificial intelligence enables computer systems to perform tasks that normally require human intelligence.
```

---

## 6. Building the RAG Prompt

The next step is to combine the retrieved context with the user's question.

A simple prompt can be structured like this:

```text
Use the following context to answer the question.

Context:
{context}

Question:
{query}

Answer using only the provided context.
If the answer cannot be found in the context, say that the information is not available.
```

This gives the LLM two important pieces of information: the user's question and the retrieved context that should be used to answer it.

---

## 7. The `rag.py` File

Today's implementation creates `src/rag.py` and reuses the existing `search()` function from Project 3.

The minimal implementation contains three main functions:

```text
build_context()
      ↓
build_prompt()
      ↓
rag_pipeline()
```

`build_context()` retrieves the relevant documents and combines them into one context string.

`build_prompt()` takes the query and retrieved context and creates the prompt that can be sent to an LLM.

`rag_pipeline()` connects these steps together and returns the query, context, and generated prompt structure.

---

## 8. Important Limitation of Today's Version

Today's minimal `rag.py` does not call an LLM yet. It prepares the retrieved context and creates the prompt that will eventually be passed to a generation model.

This is intentional. The purpose of today's build is to understand the fundamental RAG pipeline and establish the bridge between the retrieval system from Project 3 and the generation stage that will be developed in the following work.

Therefore, today's pipeline currently demonstrates:

```text
Retrieval → Context → Prompt
```

The complete RAG system will eventually become:

```text
Retrieval → Context → LLM → Answer
```

## 10. Mental Model

The easiest way to remember RAG is to think of it as two separate jobs.

The retriever answers:

> "Where is the relevant information?"

The generator answers:

> "How should I explain that information to the user?"

Together, they create:

```text
                 RAG
                  │
        ┌─────────┴─────────┐
        ↓                   ↓
   RETRIEVAL            GENERATION
        │                   │
 Find relevant          Create answer
 information              from context
        │                   │
        └─────────┬─────────┘
                  ↓
               Answer
```

## Key Concepts

| Concept | Meaning |
|---|---|
| RAG | Retrieval-Augmented Generation |
| Retrieval | Finding relevant information from a data source |
| Generation | Producing an answer using an LLM |
| Context | Retrieved information provided to the LLM |
| Retriever | Component responsible for finding relevant information |
| Query | The user's question or search request |
| Top-K | Number of relevant documents retrieved |

## One-Line Takeaway

> RAG connects retrieval with generation: first retrieve relevant information from your data, then give that context to an LLM so it can generate a grounded answer.
