## 1. Learn — Caching

Caching stores a result so the application can reuse it instead of repeating expensive work.

### Key terms

- **Cache hit:** A valid result is already stored and can be reused.
- **Cache miss:** No valid result exists, so the application performs the work.
- **TTL (Time To Live):** How long a cached result remains valid.
- **Cache invalidation:** Removing or refreshing cached results when source documents, prompts, or model settings change.

In a RAG application, response caching can avoid repeating retrieval and Gemini generation for the same request. This can reduce latency and repeated model usage.

A cache must be invalidated or versioned when the knowledge base or generation configuration changes. For streaming responses, only cache a completed answer—not a partial response after an error or cancellation.

An in-memory cache is useful for learning, but it is usually not shared between server workers and is cleared when the process restarts.

## 2. Build — Final UI polish

Review the current React interface and improve only issues you can identify. Keep the scope focused on usability and reliability rather than adding new features.

### A. Visual consistency

- Use consistent spacing between the header, messages, and composer.
- Keep typography, border radii, and colours consistent.
- Ensure text has sufficient contrast against the background.
- Check that long answers wrap correctly and remain readable.
- Make sure the chat area scrolls without moving the composer unexpectedly.

### B. Loading and streaming states

- Show a clear loading or streaming indicator while the answer is being generated.
- Prevent accidental duplicate submissions while a request is in progress.
- Keep streamed text readable as it grows.
- Ensure the loading state ends when the request completes or fails.
- Avoid leaving a permanent cursor or spinner after an error.

### C. Error handling

- Show a clear message when the backend is unavailable.
- Handle non-success HTTP responses, including rate-limit responses such as HTTP 429.
- Do not display raw stack traces or secrets to the user.
- Provide a simple way to try again after a failed request.
- Do not treat an error message as a successful answer or cache it as one.

### D. Responsive behaviour

Check the interface at desktop and narrow mobile widths:

- Header content should not overlap.
- The input and send button should remain usable.
- Messages should fit the viewport without horizontal scrolling.
- The composer should remain accessible when the message history is long.
- Buttons should have visible focus states and usable touch targets.

### E. Source information

If the backend returns source metadata, present it clearly under the relevant answer. Verify that citation IDs correspond to the actual retrieved passages. Do not display invented or hardcoded sources as if they came from the knowledge base.

## 3. Test the complete flow

Start the backend from the project root:

```cmd
uvicorn src.main:app --reload --port 8000
```

Start the frontend in a second terminal:

```cmd
cd frontend
npm run dev
```

Test the following cases:

| Test | Expected result |
|---|---|
| Submit a normal question | The request reaches FastAPI and an answer appears |
| Watch a streamed answer | Text appears progressively if streaming is enabled |
| Submit an empty question | The request is not sent |
| Backend is stopped | The UI displays a useful error |
| Backend returns an error | Loading ends and the error is visible |
| API rate limit is exceeded | The UI handles HTTP 429 clearly |
| Send a long question or receive a long answer | Text remains readable without layout breakage |
| Resize to mobile width | Controls and messages remain usable |
| Source metadata is returned | Only real sources are displayed accurately |

## 4. Review and commit

Inspect your changes:

```cmd
git status
git diff
```

Run your available tests:

```cmd
python -m pytest -v
```

If your frontend has a test or build script, run the appropriate command from `frontend`. For a typical Vite project, check `package.json` and run its available build script, often:

```cmd
npm run build
```

Commit only after reviewing the diff and confirming the application works:

```cmd
git add frontend
git commit -m "Day 149: polish RAG chat UI"
git push
```

If you also changed backend files, stage those files explicitly. Do not commit `.env`, API keys, `.venv`, `chroma_data`, or `node_modules`.
