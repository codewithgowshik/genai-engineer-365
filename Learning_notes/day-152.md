## Part 1 — LEARN: Reproducibility (30 minutes)

Reproducibility means another developer can follow your documented steps and recreate the same project setup and a comparable result.

For a RAG app, results depend on more than the source code. Document these settings:

| Item | What to record |
|---|---|
| Source corpus | File name and contents included in Git |
| Chunk size and overlap | Actual values in `src/ingestion.py` |
| Embedding model | `sentence-transformers/all-MiniLM-L6-v2` |
| Vector store | ChromaDB |
| Collection | `knowledge_base` |
| Retrieval count | Actual `top_k` in `src/retrieval.py` |
| Reranker | `cross-encoder/ms-marco-MiniLM-L-6-v2` |
| Generation model | Actual `GEMINI_MODEL` value |
| Dependencies | Versions in `requirements.txt` |

A sample corpus should be small, factual, internally consistent, and safe to publish. Keep the corpus in Git, but do not commit generated vector-store files, API keys, or `.env`.

### Step 2 — Add sample content

Open `data/documents.txt` and paste the following content. Alternatively, save it as `data/sample-knowledge-base.txt` and update your ingestion script to read that filename.

```text
DOCUMENT 1: RETRIEVAL-AUGMENTED GENERATION

Retrieval-Augmented Generation, or RAG, combines information retrieval with language generation. A RAG application searches an external knowledge source for relevant information and provides the retrieved passages to a language model as context. This allows the application to answer questions about a specific collection of documents instead of relying only on the model's training knowledge.

A typical RAG system has an indexing stage and a question-answering stage. During indexing, documents are loaded, split into chunks, converted into embeddings, and stored in a vector database. During question answering, the user's question is used to retrieve relevant chunks. The selected passages are then provided to a language model to generate an answer.


DOCUMENT 2: DOCUMENT CHUNKING

Document chunking divides a long document into smaller text sections. Retrieval systems search these sections so they can return focused passages rather than an entire large document.

Chunk size determines how much text is stored in each section. Very small chunks may lose important context. Very large chunks may contain unrelated information. Chunk overlap means neighboring chunks share some text, helping preserve information that crosses a chunk boundary.

The best chunk size and overlap depend on the source documents and the questions the application needs to answer. Metadata such as a source filename and chunk identifier helps identify where a retrieved passage came from.


DOCUMENT 3: EMBEDDINGS AND VECTOR SEARCH

An embedding is a numerical representation of text. An embedding model converts text into a vector. Text with similar meanings can have nearby vector representations.

Semantic search uses embeddings to retrieve information based on meaning, not only exact keyword matches. A vector database stores embeddings and searches for vectors similar to a query vector. ChromaDB is an example of a vector database used to store and retrieve embedded text chunks.

Semantic search is not guaranteed to find the correct passage every time. Results depend on the embedding model, source content, chunking choices, and retrieval configuration.


DOCUMENT 4: RETRIEVAL AND RERANKING

Initial retrieval finds a set of candidate passages that may be relevant to a question. The system can retrieve more candidates than it ultimately needs.

Reranking is a second-stage process that scores the relationship between the question and each candidate passage. A cross-encoder receives the question and passage together and produces a relevance score. The application can sort candidates by score and keep the highest-ranked passages.

Vector retrieval efficiently finds candidate passages using embeddings. Reranking provides a more focused relevance assessment. Reranking cannot recover a useful passage that was not included in the initial candidate set.


DOCUMENT 5: GROUNDED ANSWER GENERATION

After retrieval and reranking, the application builds a prompt containing the user's question and selected passages. The language model uses this context to generate an answer.

A grounded prompt should instruct the model to use the supplied passages as evidence, avoid inventing unsupported facts, and say when the context is insufficient. The application may ask the model to cite supporting passages.

Grounding instructions can reduce unsupported answers, but they do not guarantee correctness. The retrieved context must be relevant and sufficient, and generated answers should be evaluated.

If the retrieved passages do not contain enough information, a responsible RAG application should communicate that limitation instead of pretending the answer is supported.


DOCUMENT 6: EVALUATING A RAG APPLICATION

Retrieval evaluation checks whether the search system returns passages relevant to the question. Answer evaluation checks whether the generated response is supported by the retrieved context, answers the question, and avoids unsupported claims.

A small evaluation dataset can contain questions, expected facts, and the passages that should support each answer. It should include answerable questions and questions that cannot be answered from the sample corpus.

Latency is also important. A RAG request may spend time generating embeddings, querying the vector database, reranking passages, and calling the language model. Timing several requests is more useful than timing only one.

Evaluation reports should state the test set, method, date, and observed results. Never claim an accuracy score or benchmark result that has not actually been measured.
```

### Step 3 — Rebuild the ChromaDB index

### Step 4 — Test the sample corpus

Start your backend and frontend, then ask:

| Test question | Expected source |
|---|---|
| What does RAG stand for, and what does it combine? | Document 1 |
| What is document chunking? | Document 2 |
| Why can chunk overlap be useful? | Document 2 |
| What is an embedding? | Document 3 |
| How are vector retrieval and reranking different? | Document 4 |
| What should a grounded prompt instruct the model to do? | Document 5 |
| What is the difference between retrieval evaluation and answer evaluation? | Document 6 |

**Unanswerable test:** Ask, “What is the current population of Tokyo?” The sample corpus does not contain this information. Your application should say that the supplied documents do not provide enough information. If it invents a figure, record that as a failure to investigate.

### Step 5 — Add reproducibility instructions to README

Add a section to your root `README.md` and adjust it to match your actual ingestion command:

```markdown
## Sample Knowledge Base

The repository includes a sample corpus at `data/documents.txt`.
It covers RAG, chunking, embeddings, vector search, reranking,
grounded generation, and evaluation.

To rebuild the local vector index:
1. Create and activate the Python virtual environment.
2. Install dependencies from `requirements.txt`.
3. Configure the Gemini API key in your local `.env` file.
4. Run the ingestion script using the command documented for this project.

The ChromaDB index is generated locally in `chroma_data/` and is not
committed to the repository. Each developer builds the index from the
sample documents.
```

Record actual chunk size, overlap, model names, and tested dependency versions if known. Do not guess settings.
