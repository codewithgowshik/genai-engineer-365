# Day 124 — Multi-Query Retrieval

## Objective

Today I learned about **multi-query retrieval** and implemented it in my RAG retrieval project.

The main idea is simple: instead of searching the user's question only once, the system uses an LLM to generate several different search queries. Each query is then used to retrieve relevant documents, and the results are combined and deduplicated.

---

## What Is Multi-Query Retrieval?

Multi-query retrieval is a retrieval technique used in RAG systems to improve the chances of finding relevant information.

A user may ask a question using one particular wording. However, the information in the knowledge base may use different wording. Searching with only the original question can therefore miss useful information.

Multi-query retrieval solves this by generating multiple search queries that represent the same information need in different ways.

For example:

```text
Original question:
How do computers learn?
```

The LLM could generate queries such as:

```text
How does machine learning allow computers to learn from data?
How do computers learn patterns from data?
How does machine learning work?
```

The system then searches for each query.

---

## Basic Workflow

The workflow I implemented today is:

```text
User Question
      ↓
Google Gemini
      ↓
Generate Multiple Queries
      ↓
Query 1   Query 2   Query 3
   ↓         ↓         ↓
Retrieval Retrieval Retrieval
   ↓         ↓         ↓
Chroma    Chroma    Chroma
      \      |      /
       \     |     /
        Combine Results
              ↓
       Remove Duplicates
              ↓
       Final Documents
```

The important difference from normal semantic search is that retrieval happens multiple times using different queries.

---

## Query Rewriting vs Multi-Query Retrieval

I learned this difference from the previous day.

### Query Rewriting

Query rewriting changes the original question into **one improved query**.

```text
User Question
      ↓
     LLM
      ↓
One Rewritten Query
      ↓
   Retrieval
```

### Multi-Query Retrieval

Multi-query retrieval generates **multiple queries** from the original question.

```text
User Question
      ↓
     LLM
      ↓
Query 1
Query 2
Query 3
      ↓
Multiple Retrievals
```

So the simple difference is:

> Query rewriting = one improved query.
>
> Multi-query retrieval = several alternative queries.

---

## Why Use Multiple Queries?

Different queries can use different words while still asking for the same information.

For example, a user might ask:

```text
How do computers learn?
```

But the documents may contain:

```text
Machine learning allows computers to learn patterns from data and make predictions.
```

A generated query containing terms such as **machine learning**, **patterns**, and **data** can make it easier for semantic retrieval to find the relevant document.

Multi-query retrieval therefore aims to improve **retrieval coverage** by looking at the question from multiple query formulations.

---

## Google Gemini's Role

In today's implementation, I used **Google Gemini** to generate the search queries.

Gemini does not retrieve the documents itself in this project.

Its job is to transform the original question into several useful search queries.

The process is:

```text
Original Question
      ↓
Google Gemini
      ↓
Multiple Search Queries
```

The retrieval system then takes over:

```text
Search Query
      ↓
Embedding Model
      ↓
Chroma
      ↓
Relevant Documents
```

This separates **query generation** from **document retrieval**.

---

## The LLM Query Generation

The project uses Gemini with a prompt that asks it to generate a specific number of search queries.

The important instructions are that the queries should:

- Keep the original meaning.
- Use different wording.
- Focus on what the user wants to find.
- Help a semantic search system retrieve relevant documents.
- Not answer the question.

The generated queries are returned one per line and then converted into a Python list.

---

## Retrieval Process

After Gemini generates the queries, each query is passed to the existing `retrieve()` function.

For example:

```text
Query 1 → Chroma → Documents
Query 2 → Chroma → Documents
Query 3 → Chroma → Documents
```

The results from all searches are collected into one list.

---

## Removing Duplicates

Different queries can retrieve the same document.

For example:

```text
Query 1 → Document A, Document B
Query 2 → Document A, Document C
Query 3 → Document B, Document D
```

Without deduplication, the final result would contain repeated documents.

The project therefore removes duplicate documents before displaying the final results.

The result becomes:

```text
Document A
Document B
Document C
Document D
```

This keeps the combined result set cleaner.

## Complete Multi-Query Pipeline

The complete system I built today can be represented as:

```text
                User Question
                      ↓
                Google Gemini
                      ↓
             Multiple Queries
                ↙     ↓     ↘
          Query 1  Query 2  Query 3
             ↓        ↓        ↓
          Embedding Embedding Embedding

                 \     |     /

                      ↓
                Remove Duplicates
                      ↓

```

This is the retrieval part of a RAG system. The retrieved documents can later be passed into the generation stage to produce a grounded answer.

## Multi-Query Retrieval Advantages

The main advantage is better retrieval coverage.

A single question can be expressed in several ways. Generating multiple queries gives the retrieval system more opportunities to find relevant documents.

It can be especially useful when the wording of the user's question differs from the wording used in the knowledge base.

---

## Limitations

Multi-query retrieval also has costs and trade-offs.

First, generating multiple queries requires an LLM call.

Second, each generated query requires another retrieval operation.

Third, different queries can retrieve overlapping or irrelevant documents, which means the combined results need to be cleaned and eventually ranked.

Today's implementation uses simple duplicate removal. It does not yet perform sophisticated reranking of all combined results.
