# Day 138 — Compare Two RAG Configurations on the Metrics

**Phase:** 4 — Retrieval-Augmented Generation (RAG)  
**Week:** 20 — RAG Evaluation  
**Learn:** Evaluation frameworks (Ragas)  
**Build:** Compare two RAG configurations using evaluation metrics

## 1. Why compare RAG configurations?

A RAG system has several settings that can change its results, such as:

- How many documents are retrieved (`k`)
- How documents are split into chunks
- Which retrieval method is used
- Whether reranking is applied

Instead of choosing a configuration because it feels better, run the same evaluation questions through both configurations and compare the results.

**Important:** A comparison is only useful when both configurations use the same evaluation dataset and scoring method.

## 2. Today's comparison

We will compare two simple configurations:

| Configuration | Retrieval setting | Purpose |
|---|---|---|
| Config A — Baseline | Retrieve `k=3` chunks | Establish a baseline |
| Config B — More context | Retrieve `k=5` chunks | Check whether extra context improves results |

Keep the questions, expected answers, documents, and evaluation method the same. Only change the retrieval setting.

## 3. Metrics to compare

Use the metrics that your current evaluation code can calculate reliably.

- **Recall@k:** How many of the relevant documents were retrieved?
- **MRR (Mean Reciprocal Rank):** How high in the ranked results does the first relevant document appear?
- **Faithfulness:** Is the generated answer supported by the retrieved context?
- **Answer relevance:** Does the answer address the user's question?

Do not invent scores. Record actual results from your evaluation run. If a metric is not implemented yet, mark it as `Not measured`.

## 4. Today's build

Create a small script that runs the same evaluation set against both retrieval configurations.

Example retrieval comparison using the existing `retrieve(query, k=3)` function:

```python
from src.retrieval import retrieve

def run_config(query: str, k: int) -> list[str]:
    results = retrieve(query, k=k)
    return results["documents"][0]

query = "Put one question from your evaluation set here."

config_a_docs = run_config(query, k=3)
config_b_docs = run_config(query, k=5)

print("CONFIG A — k=3")
for index, document in enumerate(config_a_docs, start=1):
    print(f"{index}. {document}")

print("\nCONFIG B — k=5")
for index, document in enumerate(config_b_docs, start=1):
    print(f"{index}. {document}")
```

This example compares retrieved context only. To compare faithfulness or answer relevance, also generate an answer for each configuration and run the same judge or evaluation method on both.

### Record the results

Create a table in your notes or a CSV file:

| Metric | Config A (`k=3`) | Config B (`k=5`) | Better result |
|---|---:|---:|---|
| Recall@k | Not measured | Not measured | Not measured |
| MRR | Not measured | Not measured | Not measured |
| Faithfulness | Not measured | Not measured | Not measured |
| Answer relevance | Not measured | Not measured | Not measured |
| Average latency (optional) | Not measured | Not measured | Not measured |

Replace `Not measured` only after you have run the evaluation. A higher `k` is not automatically better: more context can improve recall, but it can also add irrelevant information or increase latency.

## 5. How to interpret the comparison

After running the evaluation, ask:

1. Did Config B retrieve relevant evidence that Config A missed?
2. Did answer faithfulness improve, decline, or stay similar?
3. Did answer relevance change?
4. Did latency increase enough to matter?
5. Which configuration gives the best balance for this dataset?

Do not select a winner from one question alone. Use the complete evaluation set and investigate surprising results.

## Key takeaways

- Compare configurations using the same evaluation questions and scoring method.
- Change one setting at a time so the comparison is meaningful.
- More retrieved context does not always mean better answers.
- Record real measurements; never fill in guessed metric scores.
- Keep evaluation results and unresolved tool errors transparent.
