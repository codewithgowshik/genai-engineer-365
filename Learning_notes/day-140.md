# Day 140 — Fix the Worst RAG Failure Mode

**Phase:** 4 — Retrieval-Augmented Generation (RAG)  
**Week:** 20 — RAG Evaluation  
**Learn:** Tracking evaluation across iterations  
**Build:** Fix the worst failure mode  

## 1. Why track evaluation across iterations?

A single evaluation run is a snapshot. Repeating the same test set after each change helps show whether the system is improving, getting worse, or trading one weakness for another.

For each run, record the run ID and date, configuration and code change, evaluation dataset/version, metrics actually measured, failures observed, and the fix's outcome. Keep the test set and scoring method consistent when comparing runs. If either changes, record that too.

## 2. Find the worst failure mode

Inspect failed cases in the latest evaluation log before changing code.

Common RAG failure modes include:

- **Retrieval miss:** Relevant evidence is not retrieved.
- **Poor ranking:** Relevant evidence is retrieved but appears too low.
- **Insufficient context:** Retrieved chunks omit information needed to answer.
- **Unsupported answer:** The model states something not supported by the context.
- **Irrelevant answer:** The answer does not address the question.
- **Evaluation/tooling failure:** The evaluation script or framework fails before producing trustworthy results.

Choose the failure supported by your actual logs. Do not assume which one is worst before reviewing the data. If Ragas is still blocked, record that as a tooling blocker and use only metrics your own code can calculate.

## 3. Today's build

1. Open `data/eval_results.csv` and identify the most frequent or consequential failure.
2. Select one failure mode to fix first.
3. Make one targeted change instead of changing several pipeline components at once.
4. Run the same evaluation cases before and after the change.
5. Compare available metrics and inspect affected examples.
6. Record the change, result, and any regression.

### Example: retrieval returns too little context

If logs show relevant chunks are missing, compare `k=3` with `k=5` using the same test questions. Keep the change only if the results support it. More context can increase recall but may also add noise and latency.

### Example: answers are unsupported by relevant context

Inspect the prompt in `src/llm.py`. Consider instructing the model to answer only from supplied context, cite supporting evidence if your implementation supports citations, and say when the context does not contain the answer. Re-run the same cases and check for regressions.

### Example: evaluation cannot run

If the Ragas import issue from Day 137 remains unresolved, do not report Ragas scores. Record the error, use available retrieval metrics or manual inspection, and mark unsupported metrics `Not measured`.

## 4. Track results across iterations

Add a row to a run-summary file or a section in your notes for each meaningful change.

| Run | Change | Dataset | Metrics measured | Outcome |
|---|---|---|---|---|
| Baseline | Initial configuration | Same evaluation set | Record actual metrics | Establish baseline |
| Iteration 1 | One targeted fix | Same evaluation set | Record actual metrics | Keep, revert, or investigate |

Do not fill this table with guessed values. Include a representative failure before the fix and what happened after it.

## Key takeaways

- Track evaluation runs so changes can be compared over time.
- Choose the failure mode from evidence, not intuition.
- Change one thing at a time and re-test on the same cases.
- Keep measured results separate from assumptions.
- RAG and fine-tuning address different needs; neither is universally better.
