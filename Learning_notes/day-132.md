## 1. What is a corpus?

A **corpus** is the collection of documents that your system searches. In this project, the documents are stored in `data/documents.txt` and indexed in Chroma.

A larger corpus can improve the chance of finding useful information, but it can also increase ingestion time, embedding costs, storage requirements, and the difficulty of evaluating retrieval quality.

## 2. The current ingestion and retrieval flow

```text
data/documents.txt
       ↓
Load documents
       ↓
Create embeddings
       ↓
Store vectors in Chroma
       ↓
Embed the user's query
       ↓
Retrieve the top-k matching documents
```

- **Ingestion** prepares documents and stores them in the vector database.
- **Embedding** converts text into numerical vectors that represent semantic meaning.
- **Retrieval** finds documents that are close to the query in embedding space.
- **Top-k** means returning the `k` highest-ranked results, such as the top 3.

## 4. Measuring elapsed time with `time.perf_counter()`

`time.perf_counter()` is a high-resolution timer intended for measuring elapsed time.

```python
import time

start_time = time.perf_counter()
# Run the operation you want to measure
end_time = time.perf_counter()

duration = end_time - start_time
print(f"Time taken: {duration:.4f} seconds")
```

- `start_time` records the timer before the operation.
- `end_time` records it after the operation.
- Subtracting the two gives the elapsed duration.
- `:.4f` formats the result to four digits after the decimal point. For example, `0.123456` becomes `0.1235`.

### In the retrieval test

```python
start_time = time.perf_counter()
results = retrieve(query, k=3)
end_time = time.perf_counter()
latency = end_time - start_time
```

This measures the time spent inside `retrieve()` for that query. With the current implementation, that includes query embedding and Chroma retrieval. It does **not** include model loading that happened earlier during module import, and it does not measure the separate ingestion process.

## 5. What the scale test measures

The test runs five sample questions, retrieves the top 3 documents for each, prints the results, and reports each query's latency and the average latency.

Average latency is calculated as:

```text
average latency = total latency across queries / number of queries
```

Record actual measurements rather than guessing. To compare a smaller corpus with a larger corpus fairly, use the same machine, same test questions, same `k` value, and same timing method for both runs.

A simple results table:

Do not assume the larger corpus is automatically better. Check both speed and relevance.

## 6. Important limitations

- Five queries provide only a small sample, not a complete benchmark.
- Timing can vary due to machine load, caching, and other background activity.
- A larger corpus may return more relevant information, but it can also introduce distracting documents.
- The test measures retrieval latency, not end-to-end RAG answer-generation latency.
- The current experiment does not prove that performance scales well to thousands or millions of documents; it is an introductory measurement.

## 7. Key terms

| Term | Meaning |
|---|---|
| Corpus | The collection of documents being searched |
| Ingestion | Preparing documents and adding them to the search index |
| Embedding | A numerical vector representing text meaning |
| Vector database | A database designed to store and search vectors |
| Retrieval latency | Time taken to retrieve results for a query |
| `perf_counter()` | A high-resolution timer used to measure elapsed time |
| Benchmark | A repeatable test used to compare performance |
| Incremental ingestion | Processing new or changed documents instead of rebuilding everything |
