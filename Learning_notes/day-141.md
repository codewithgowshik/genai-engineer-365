# Day 141 — Define and Design Project 4: Production RAG App

**Phase:** 4 — Retrieval-Augmented Generation (RAG)  
**Week:** 21 — Build Project 4 (Production RAG App)  
**Learn:** Defining the product  
**Build:** Create the Project 4 repository and design it

## 1. What does it mean to define the product?

Before writing code, decide what problem the application solves, who it is for, and what the first useful version must do.

A production-oriented RAG app should help users ask questions about a defined knowledge source and receive answers grounded in retrieved evidence. For this first design session, keep the scope small: define one use case, the intended user, the input documents, the expected answer format, and how you will know whether the app works.

## 2. Define the product

Use this product brief and adjust it to fit your project.

- **Working name:** Production RAG App
- **Problem:** Users need to find answers in documents without manually searching every file.
- **Target user:** Someone who needs answers from a specific set of documents.
- **Input:** Supported documents and a user's question.
- **Output:** An answer grounded in retrieved context, with source information where available.
- **Core value:** Make document-based question answering easier to use, inspect, and evaluate.

### Minimum viable product (MVP)

1. Load a small collection of documents.
2. Split documents into chunks and create embeddings.
3. Store chunks and metadata in a vector database.
4. Retrieve relevant chunks for a question.
5. Generate an answer using retrieved context.
6. Show the answer and source references where available.
7. Handle questions that cannot be answered from the available context.
8. Log basic evaluation and error information.

Avoid adding complex authentication, multi-user permissions, or deployment infrastructure before the basic question-answering flow works, unless your requirements need them.

## 3. Design the system architecture

```text
Documents
   |
   v
Ingestion and validation
   |
   v
Chunking and metadata
   |
   v
Embedding model
   |
   v
Vector database
   |
   v
User question --> Query embedding --> Retrieval
                                  |
                                  v
                         Optional reranking
                                  |
                                  v
                       Context + question
                                  |
                                  v
                             LLM answer
                                  |
                                  v
                     Answer + source references
```

Keep ingestion separate from question answering. Ingestion prepares the knowledge base; query-time retrieval finds relevant evidence for each question.

## 4. Choose a first-pass technology stack

Reuse tools you already understand where they fit. For example:

- **Language:** Python
- **API:** FastAPI or a framework you already know
- **Embeddings:** Sentence Transformers
- **Vector database:** ChromaDB
- **Generation:** Your existing LLM provider integration
- **Configuration:** Environment variables in a local `.env` file
- **Testing:** pytest or repeatable test scripts
- **Version control:** Git and GitHub

These are initial options, not mandatory decisions. Document your actual choices in the README. Never commit `.env` or API keys.

## 5. Create the repository

Choose a name such as `production-rag-app` and create a structure like this:

```text
production-rag-app/
├── data/
│   └── .gitkeep
├── src/
│   ├── __init__.py
│   ├── ingestion.py
│   ├── retrieval.py
│   ├── generation.py
│   └── main.py
├── tests/
│   └── .gitkeep
├── .env.example
├── .gitignore
├── README.md
└── requirements.txt
```

### PowerShell commands

```powershell
mkdir production-rag-app
cd production-rag-app

git init
python -m venv .venv
.\.venv\Scripts\Activate.ps1

New-Item -ItemType Directory -Force src, data, tests
New-Item -ItemType File -Force src\__init__.py
New-Item -ItemType File -Force README.md, .gitignore, .env.example, requirements.txt
New-Item -ItemType File -Force data\.gitkeep, tests\.gitkeep
```

If activation is blocked by PowerShell policy, use the virtual environment's Python directly or resolve the policy issue according to your machine's setup.

## 6. Add the initial project files

### `.gitignore`

```gitignore
.venv/
venv/
__pycache__/
*.py[cod]
.env
.pytest_cache/
chroma_data/
data/*
!data/.gitkeep
```

If you later decide to version non-sensitive sample documents or evaluation data, update the ignore rules deliberately. Do not commit private documents or generated data accidentally.

### `.env.example`

```dotenv
# Copy to .env and add your own local values.
LLM_API_KEY=
```

Replace `LLM_API_KEY` with the variable your chosen provider actually expects. Keep the real key only in `.env`.

### `requirements.txt`

Start with only the packages required by your implementation. For the suggested stack, initial dependencies may include:

```text
fastapi
uvicorn
chromadb
sentence-transformers
python-dotenv
pytest
```

Add your LLM provider SDK when implementing generation. Install and test dependencies in a virtual environment, then record compatible versions after confirming the project runs. Don't copy potentially incompatible packages from the earlier Ragas environment without checking them.

## 7. Write the README

Your README should explain:

1. What the app does.
2. Who it is for.
3. The planned MVP.
4. The architecture.
5. The technology choices.
6. How to set up and run the app.
7. How retrieval and answer quality will be evaluated.
8. Which features are planned but not implemented.

Clearly label planned features as planned. Do not describe functionality as complete until it works.

## Key takeaways

- Define the user problem and MVP before coding.
- Separate document ingestion from query-time retrieval.
- Start with a small architecture you can test end to end.
- Keep credentials, private documents, and generated local databases out of Git.
- Document the difference between planned features and implemented features.
