# Day 126 — Debugging Retrieval

## Objective

Today I learned how to debug a RAG retrieval system by inspecting the chunks returned by the retriever instead of looking only at the final answer.

The main idea is simple:

> If a RAG answer is wrong, first check what information was retrieved and given to the LLM.

## What Is Retrieval Debugging?

A RAG system normally follows this flow:

```text
User Question
      ↓
Query Processing
      ↓
Retrieval
      ↓
Retrieved Chunks
      ↓
Context
      ↓
LLM
      ↓
Answer
```

Retrieval debugging focuses on the part between retrieval and context.

```text
Retrieval
    ↓
Retrieved Chunks
    ↓
Inspect
```

Instead of only checking whether the final answer looks correct, I inspect the actual chunks returned by the retrieval system.

## Why Retrieved Chunks Matter

An LLM cannot reliably use information that was never retrieved and placed into its context.

For example, if the user asks:

```text
What is the capital of the United Kingdom?
```

A useful retrieved chunk would be:

```text
London is the capital of the United Kingdom.
```

But if the retriever returns unrelated information such as:

```text
Python is a programming language.
Coffee is a widely consumed beverage.
```

then the problem occurred during retrieval, before the answer-generation stage.

## What I Should Inspect

When debugging retrieval, I should inspect several pieces of information.

### 1. Original Query

First, check the question that was sent to the retrieval system.

This tells me exactly what the user wanted to find.

### 2. Retrieved Chunks

Look at the actual documents or chunks returned by the retriever.

I need to ask:

- Are they relevant to the question?
- Do they contain the information needed to answer it?
- Are they unrelated?
- Is important information missing?

### 3. Scores or Distances

Inspect the retrieval scores or distances when they are available.

These help show how strongly each result was ranked by the retrieval system.

### 4. Source and Metadata

Check where each retrieved chunk came from and inspect useful metadata such as:

```text
source
parent_id
 topic
```

This can help identify where a bad result originated.

## Common Retrieval Failures

### Failure 1 — Wrong Document

The system retrieves a document that has little or nothing to do with the question.

Example:

```text
Question:
What is semantic search?

Retrieved:
Coffee is a widely consumed beverage.
```

This indicates a retrieval-quality problem.

### Failure 2 — Relevant but Incomplete Chunk

The retrieved chunk is related to the question, but important information is missing because the text was split into chunks.

This connects to the chunking work from earlier days.

Chunk size and overlap can affect how much useful context is available in each retrieved chunk.

### Failure 3 — Correct Result Ranked Too Low

The correct document may exist in the database, but another document appears above it in the results.

Possible factors include:

- `k`
- semantic similarity
- query wording
- keyword weighting
- hybrid ranking

## Separating Different Types of RAG Problems

Inspecting retrieval helps identify where the failure happened.

### Retrieval Problem

The wrong chunks were retrieved.

```text
Wrong chunks
    ↓
Retrieval problem
```

### Context or Prompt Problem

The correct information was retrieved, but the context was not constructed or passed correctly.

```text
Correct chunks
    ↓
Bad context/prompt
    ↓
Problem
```

### Generation Problem

The correct context was given to the LLM, but the generated answer was still poor.

```text
Correct context
    ↓
LLM
    ↓
Poor answer
```

This separation makes debugging much easier.

## Today's Debugging Workflow

For each test question, inspect:

```text
Query
  ↓
Retrieved Chunks
  ↓
Scores / Distances
  ↓
Metadata / Source
```

Then decide whether the retrieved information is actually useful for answering the question.

## Example Test Questions

I can test retrieval using questions such as:

```text
How do computers learn from data?
```

```text
What is semantic search?
```

```text
What is the capital of the United Kingdom?
```

I can also test an unsupported question such as:

```text

```

The purpose is to see what the retriever actually returns rather than assuming that the retrieval is correct.

## What I Learned Today

- RAG debugging should start by inspecting retrieved context.
- A wrong answer does not automatically mean the LLM is the problem.
- The retrieved chunks determine what information is available to the generation stage.
- Retrieval failures can include wrong documents, incomplete chunks, or correct results ranked too low.
- Scores, distances, sources, and metadata can help diagnose retrieval problems.
- Debugging helps separate retrieval problems from context/prompt problems and generation problems.
