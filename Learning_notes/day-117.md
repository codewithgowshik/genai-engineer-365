## Chunking Strategies, Revisited

Chunking is the process of splitting a large document into smaller pieces before generating embeddings. The retriever searches these smaller pieces and passes the most relevant ones to the language model.

The basic process is:

```text
Large Document
      ↓
Chunking
      ↓
Smaller Chunks
      ↓
Embeddings
      ↓
Vector Database
      ↓
Retrieval
      ↓
Relevant Context
      ↓
LLM
```

Chunking is important because the size of the chunks can affect the quality of retrieval. The system needs chunks that contain enough information to be useful while avoiding unnecessary information.

## Smaller Chunks

Smaller chunks can make retrieval more specific because each chunk contains a smaller amount of information. For example, if a document contains several different topics, smaller chunks can allow the retriever to select only the section related to the user's question.

However, very small chunks can lose important context. A sentence by itself may not contain enough information to explain the subject properly. Therefore, smaller chunks provide more specificity but can provide less context.

## Larger Chunks

Larger chunks preserve more surrounding information. This can be useful when understanding a topic requires information from multiple sentences. However, larger chunks can also contain information that is not relevant to the user's question.

This creates a basic trade-off:

```text
Small chunks
→ More specific
→ Less context

Large chunks
→ More context
→ Potentially less precise
```

There is no single chunk size that is automatically correct for every RAG application. The appropriate approach depends on the documents and the type of questions users will ask.

## Connecting Chunking to RAG

Chunking happens before retrieval, but its effect is visible during retrieval and generation.

The overall relationship is:

```text
Documents
    ↓
Chunking
    ↓
Embeddings
    ↓
Vector Database
    ↓
Retrieval
    ↓
Relevant Chunks
    ↓
Context
    ↓
LLM
    ↓
Answer
```

If the chunks are poorly designed, the retriever may return incomplete or irrelevant information. This can then affect the quality of the final generated answer.

This is why chunking is an important part of building a RAG system.

## What Does Grounded Mean?

A grounded answer is an answer that is based on the information provided in the retrieved context. The goal is to make the LLM use the retrieved information rather than answering without reference to the context.

A simple prompt can instruct the model:

```text
Use the following context to answer the question.

Context:
{retrieved_context}

Question:
{user_question}

Answer using only the provided context.
If the answer cannot be found in the context, say that the information is not available.
```

The important instruction is:

```text
Answer using only the provided context.
```

This creates a clear connection between retrieval and generation.

## Example

Suppose the user asks:

```text
How do computers learn from data?
```

The retriever might return:

```text
Machine learning allows computers to learn patterns from data.
```

The RAG prompt then becomes:

```text
Context:
Machine learning allows computers to learn patterns from data.

Question:
How do computers learn from data?
```

The LLM can generate a natural-language answer using the retrieved information. The answer is considered grounded because the relevant information came from the retrieved context.

## Testing a Grounded Answer

A useful test is to ask a question that is supported by the sample dataset.

For example:

```text
How do computers learn from data?
```

The system should retrieve information about machine learning and use that information when generating the answer.

I should also test a question for which the dataset does not contain useful information.

For example:

```text
What is the recipe for making chocolate cake?
```

If the retrieved context does not contain information about chocolate cake, the prompt instructs the model to say that the information is not available.

This is an important test because the goal is not simply to make the LLM answer every question. The goal is to make the answer depend on the retrieved information.

## Retrieve → Augment → Generate

The three stages of RAG can now be connected clearly.

**Retrieve** means finding relevant information from the stored data.

**Augment** means adding that retrieved information to the user's question as context.

**Generate** means using the question and retrieved context to produce the final answer.

The complete idea is:

```text
RETRIEVE
Find relevant information.
        ↓
AUGMENT
Add the information to the prompt.
        ↓
GENERATE
Use the context to produce an answer.
```

This is the core idea behind Retrieval-Augmented Generation.
