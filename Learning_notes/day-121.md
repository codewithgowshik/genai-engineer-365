# Day 121 — Implement Parent-Document Retrieval

## Objective

Today I learned about parent-document retrieval, also called small-to-big retrieval. The goal is to improve RAG retrieval by using small chunks to find precise information while returning a larger parent document to the LLM so it has enough surrounding context to generate a better grounded answer.

This builds directly on the chunking experiments from Day 120. Smaller chunks can improve retrieval precision, but they can sometimes contain too little context. Parent-document retrieval addresses this trade-off by separating the text used for retrieval from the larger text used as generation context.

## The Problem with Small Chunks

In a basic RAG system, a large document is divided into smaller chunks. These chunks are embedded and stored in a vector database. When the user asks a question, the system searches the vector database and returns the most similar chunks.

The problem is that a very small chunk may contain the exact information needed to match the question but may not contain enough surrounding information for the LLM to fully understand the topic.

The basic flow is:

```text
Large Document
      ↓
Small Chunks
      ↓
Retrieve One Small Chunk
      ↓
LLM Receives Small Context
```

This can give precise retrieval but sometimes insufficient context.

## What Is Parent-Document Retrieval?

Parent-document retrieval keeps two levels of text: smaller child chunks and larger parent documents.

The small child chunks are used for vector search because they make retrieval more precise. Each child chunk keeps a reference to the larger parent document or section it came from.

When a child chunk matches the user's question, the system uses its parent ID to find the larger parent document. The parent is then provided as context to the LLM.

The basic idea is:

```text
Small Child Chunk
       ↓
Find Relevant Information
       ↓
Parent Document
       ↓
Provide More Context
       ↓
LLM
```

This is also called **small-to-big retrieval** because the system searches small pieces but expands the result to a larger piece of information before generation.

## Parent and Child Relationship

A simple structure can look like this:

```text
parent1
 ├── chunk1
 ├── chunk2
 └── chunk3

parent2
 ├── chunk4
 ├── chunk5
 └── chunk6
```

Each child chunk needs to remember which parent it belongs to. For example:

```python
metadata = {
    "parent_id": "parent1"
}
```

The metadata creates the connection between the small searchable chunk and the larger parent document.

## Example

Suppose the parent text contains:

```text
Machine learning allows computers to learn patterns from data.
Deep learning is a branch of machine learning that uses neural
networks with multiple layers.
Machine learning can be used for prediction and classification.
```

This parent can be divided into smaller child chunks such as:

```text
Child 1:
Machine learning allows computers to learn patterns from data.

Child 2:
Deep learning is a branch of machine learning...
```

If the user asks:

```text
How do computers learn from data?
```

the vector search may identify Child 1 as the relevant chunk.

Instead of sending only Child 1 to the LLM, the system can use its `parent_id` to retrieve the complete parent text. The LLM then receives the larger context containing the surrounding information.

## Today's RAG Flow

The RAG pipeline before parent-document retrieval was approximately:

```text
User Question
      ↓
Query Embedding
      ↓
Search Vector Database
      ↓
Retrieve Relevant Chunks
      ↓
Use Chunks as Context
      ↓
LLM
      ↓
Grounded Answer
```

With parent-document retrieval, the flow becomes:

```text
User Question
      ↓
Query Embedding
      ↓
Search Child Chunks
      ↓
Find Matching Child
      ↓
Read Parent ID
      ↓
Retrieve Parent Document
      ↓
Use Parent as Context
      ↓
LLM
      ↓
Grounded Answer
```

The important change is the extra step between retrieval and generation.

## Why Use Small Chunks for Retrieval?

Small chunks can make semantic retrieval more precise because each vector represents a relatively focused piece of information. This can make it easier for the query embedding to find the part of a document that is actually related to the question.

However, making chunks smaller can also remove useful surrounding context. Parent-document retrieval lets the system keep the retrieval unit small without forcing the LLM to work with only that small piece.

The key idea is:

> **Retrieve small, understand big.**

## Implementation Concept

For today's implementation, the system needs to keep a relationship between every child chunk and its parent.

Conceptually:

```text
Parent Document
      ↓
Create Child Chunks
      ↓
Store Child Chunk + parent_id
      ↓
Embed Child Chunks
      ↓
Store in Vector Database
```

During a search:

```text
Question
   ↓
Retrieve Child Chunks
   ↓
Read parent_id
   ↓
Find Parent Document
   ↓
Build Larger Context
   ↓
LLM
```

The vector database is therefore mainly used to find the relevant child chunks, while the parent relationship is used to recover the larger context.

## Connection to Previous Days

Day 120 focused on chunk size and overlap. That experiment showed why the size of the retrieval unit matters.

Day 121 builds on that idea. Instead of trying to make one chunk size work perfectly for both retrieval and generation, parent-document retrieval allows the system to use a smaller unit for retrieval and a larger unit for generation.

This gives the RAG system two useful levels:

```text
Child chunk → precise retrieval
Parent document → richer context
```

## Key Concepts

**Parent document:** The larger section or document that contains the information represented by one or more child chunks.

**Child chunk:** A smaller piece of the parent used for semantic retrieval.

**Parent ID:** Metadata that connects a child chunk to its parent.

**Small-to-big retrieval:** Retrieve a small relevant piece first, then expand it to a larger parent context.

**Retrieval precision:** How specifically the system can identify information relevant to the question.

**Context:** The information provided to the LLM so that it can generate a grounded answer.
