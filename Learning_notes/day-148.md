## 1. Learn — Caching in a RAG application

A RAG request usually performs query embedding, vector retrieval, reranking, and LLM generation. Repeating the same question may repeat this work and incur another LLM API call.

A response cache can store completed answers and return them for repeated questions.

### Key terms

- **Cache hit:** A matching result is already stored.
- **Cache miss:** No valid matching result is available, so the application computes a fresh result.
- **TTL (Time To Live):** The time a cached entry remains valid.
- **Cache invalidation:** Removing or refreshing cached entries when documents, prompts, or model configuration change.

For a streaming endpoint, collect generated chunks while sending them to the client. Store the response only after generation completes successfully. If generation fails or is cancelled, do not cache a partial answer.

A cache key should account for more than the raw question when necessary. Include a knowledge-base version and relevant model/prompt configuration so an old answer is not reused after the underlying system changes.

## 2. Learn — Rate limiting

Rate limiting restricts how frequently a client can call an API. For example, a limit of `10/minute` permits up to ten requests within the configured time window.

When a client exceeds the limit, the API should return **HTTP 429 — Too Many Requests**.

Rate limiting can protect API capacity and reduce accidental or abusive request volume. An in-memory, IP-based limiter is a learning-friendly starting point, but it has limitations:

- Limits may be separate for each worker or process.
- IP addresses may not reliably identify individual users.
- A multi-instance deployment generally needs shared storage, such as Redis.
- Authenticated applications should consider limiting by user identity.

## 3. Build — Create an in-memory response cache

Create `src/cache.py`:

```python
import time
from threading import Lock


class ResponseCache:
    def __init__(self, ttl_seconds=300):
        self.ttl_seconds = ttl_seconds
        self._cache = {}
        self._lock = Lock()

    def get(self, key):
        with self._lock:
            item = self._cache.get(key)

            if item is None:
                return None

            value, expires_at = item

            if time.monotonic() >= expires_at:
                del self._cache[key]
                return None

            return value

    def set(self, key, value):
        with self._lock:
            self._cache[key] = (
                value,
                time.monotonic() + self.ttl_seconds,
            )


response_cache = ResponseCache(ttl_seconds=300)
```

This cache stores values in process memory for five minutes. It is thread-safe for basic access, but it does not persist across restarts or share entries between worker processes. It also has no size limit, so a production implementation should add eviction or use a managed cache.

## 4. Integrate caching with streaming

For the chat endpoint, the intended flow is:

1. Normalize the question.
2. Build a cache key that includes the question and relevant knowledge-base/model/prompt version.
3. Check the cache.
4. On a cache hit, stream the stored answer without calling Gemini.
5. On a cache miss, retrieve and rerank passages, then generate the answer.
6. Stream each generated chunk while collecting it.
7. Cache the completed answer only after successful generation.

Be careful not to cache an answer that was only partially generated. If your API later returns structured citations alongside the answer, cache that response structure as well.

## 5. Build — Rate limiting with SlowAPI

Install the dependency in your active virtual environment:

```cmd
pip install slowapi
```

Add this to `requirements.txt`:

```text
slowapi
```

The endpoint limit can be expressed using a decorator such as:

```python
@limiter.limit("10/minute")
```

This is only the limit declaration; SlowAPI also requires the limiter to be configured on the FastAPI application, the request to be available to the limited endpoint, and an exception handler to be registered. Follow the package's FastAPI integration requirements when wiring it into `src/main.py`.

For a local learning project, IP-based limiting is a reasonable starting point. For production, choose a trustworthy identity and shared storage where multiple workers or instances must enforce the same limit.
