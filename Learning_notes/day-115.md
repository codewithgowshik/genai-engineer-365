## RAG, Fine-Tuning, and Long Context

RAG, fine-tuning, and long context are different ways of giving an AI system access to information or adapting how it responds.

RAG stands for Retrieval-Augmented Generation. Instead of changing the model itself, RAG retrieves relevant information at the time of a user's question and provides that information to the language model as context.

The basic RAG flow is:

```text
User Question
      ↓
Retrieve Relevant Information
      ↓
Add Information as Context
      ↓
LLM
      ↓
Generated Answer
```

RAG is useful when the information comes from documents or data that can be updated independently of the language model. Instead of retraining the model whenever the source information changes, the retrieval data can be updated.

## Fine-Tuning

Fine-tuning is different from RAG because it involves further training a model on a specific dataset.

The simplified idea is:

```text
Base Model
    ↓
Training Data
    ↓
Further Training
    ↓
Fine-Tuned Model
```

Fine-tuning changes the model's learned parameters. RAG does not require changing the model's parameters; instead, it provides relevant information during the request.

This means RAG and fine-tuning solve different problems and should not be treated as interchangeable techniques.

## Long Context

Long-context approaches allow a model to receive a large amount of information directly in its context.

The simplified flow is:

```text
Large Amount of Context
          ↓
         LLM
          ↓
       Answer
```

If the information fits within the model's context window, it may be possible to provide the information directly without building a retrieval system.

The important distinction is that RAG retrieves relevant pieces of information, while long context allows a large amount of information to be provided directly to the model.

## Simple Comparison

| Approach | Main Idea |
|---|---|
| RAG | Retrieve relevant information and provide it to the LLM |
| Fine-tuning | Further train the model on specific data |
| Long context | Provide a large amount of information directly in the context |

## Embedding the Chunks

On Day 114, I loaded the documents and split them into chunks. Today, those chunks need to be converted into embeddings.

An embedding is a numerical representation of text. The embedding model converts each chunk into a vector that represents information about the meaning of that text.

For example:

```text
"Machine learning allows computers to learn patterns from data."
                         ↓
                  Embedding Model
                         ↓
              Numerical Vector
```

The exact values in the vector are generated by the embedding model. I do not need to manually interpret each number. The important point is that these vectors allow the system to compare chunks based on semantic similarity.

## Using the Embedding Model

For this project, I am using the same embedding model I worked with during Project 3:

```text
all-MiniLM-L6-v2
```

The basic process is:

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("all-MiniLM-L6-v2")

embeddings = model.encode(chunks)
```

The result is a collection of numerical vectors corresponding to the chunks.

## Storing the Chunks in Chroma

After generating the embeddings, the next step is to store the chunks and their vectors in Chroma.

Chroma is the vector database used in this project. It allows the application to store documents together with their embeddings and later perform similarity searches.

The basic storage flow is:

```text
Chunk
  ↓
Embedding
  ↓
Chroma
```

The chunks need unique IDs so that they can be identified later.

For example:

```python
ids = []

for i in range(len(chunks)):
    ids.append(f"chunk{i + 1}")
```

The chunks and embeddings can then be stored in a Chroma collection.

## Why Store Embeddings?

The reason for storing embeddings is that the retrieval stage needs to compare a user's query with the stored information.

When a user asks a question later, the question will also be converted into an embedding.

The system can then compare the query embedding with the stored chunk embeddings and retrieve the most relevant chunks.

The future retrieval flow will look like:

```text
User Question
      ↓
Query Embedding
      ↓
Compare With Stored Vectors
      ↓
Find Similar Chunks
      ↓
Retrieve Relevant Context
```

This is the foundation that allows semantic retrieval to work.

## Why Store Chunks Instead of Only Whole Documents?

The reason for chunking is to make retrieval more focused.

A large document might contain many different topics. If the entire document is stored as one vector, a search may retrieve a large amount of information even though only one small section is relevant.

With chunks, the system can retrieve smaller pieces of information.

For example:

```text
Large Document
      ↓
Chunk 1
Chunk 2
Chunk 3
Chunk 4
      ↓
Individual Embeddings
      ↓
Semantic Retrieval
```

This allows the retrieval system to identify the specific pieces that are most relevant to a user's question.
