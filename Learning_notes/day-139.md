## 1. What is a RAG test set?

A test set is a collection of representative questions used to check how well a RAG system performs. Depending on the metrics you want to calculate, each test case may contain:

- A question
- A reference answer
- The expected relevant document or evidence
- The system's generated answer
- The retrieved context

Use questions that reflect the kinds of queries your system is meant to answer. Keep the test set consistent when comparing configurations so that changes in scores reflect the configuration rather than a different set of questions.

## 2. What makes a useful test set?

A useful test set should be representative, consistent, clear, traceable, and honest about gaps. Start with the existing `data/eval_set.json` file and inspect its structure before changing it. Do not overwrite existing test cases without checking their format.

## 3. Today's build

Create a repeatable log of evaluation results. A CSV file is useful for reviewing results in a spreadsheet or analysing them later.

Suggested columns:

| Column | Meaning |
|---|---|
| `run_id` | Identifier for this evaluation run |
| `timestamp` | When the evaluation ran |
| `config_name` | For example, `k3_baseline` or `k5_context` |
| `question_id` | Stable test-question ID |
| `question` | Evaluation question |
| `retrieved_k` | Number of chunks requested |
| `retrieved_context` | Context returned by retrieval |
| `answer` | Generated answer, if available |
| `recall_at_k` | Retrieval recall, if implemented |
| `mrr` | Mean Reciprocal Rank, if implemented |
| `faithfulness` | Faithfulness score, if implemented |
| `answer_relevance` | Answer relevance score, if implemented |
| `latency_ms` | Runtime in milliseconds, if measured |
| `notes` | Errors, missing metrics, or observations |

Use `Not measured` for metrics you have not implemented. Do not enter fabricated scores. If your code already has an established results format, extend it rather than creating a conflicting one.

## 4. Example results-log script

This starting point logs retrieved context and timing. It does **not** calculate Recall@k, MRR, faithfulness, or answer relevance. Add those scores only when your evaluation code produces them.

Save as `src/log_eval_results.py` if it fits your project structure:

```python
import csv
import json
import time
from datetime import datetime, timezone
from pathlib import Path

from src.retrieval import retrieve

EVAL_PATH = Path("data/eval_set.json")
OUTPUT_PATH = Path("data/eval_results.csv")

FIELDNAMES = [
    "run_id", "timestamp", "config_name", "question_id", "question",
    "retrieved_k", "retrieved_context", "answer", "recall_at_k", "mrr",
    "faithfulness", "answer_relevance", "latency_ms", "notes",
]


def load_questions():
    with EVAL_PATH.open("r", encoding="utf-8") as file:
        data = json.load(file)

    # Adjust this after inspecting your actual eval_set.json structure.
    if isinstance(data, list):
        return data
    if isinstance(data, dict) and isinstance(data.get("questions"), list):
        return data["questions"]

    raise ValueError(
        "Unknown eval_set.json structure. Inspect it and update load_questions()."
    )


def main():
    questions = load_questions()
    OUTPUT_PATH.parent.mkdir(parents=True, exist_ok=True)
    run_id = datetime.now(timezone.utc).strftime("run_%Y%m%dT%H%M%SZ")
    timestamp = datetime.now(timezone.utc).isoformat()
    file_exists = OUTPUT_PATH.exists()

    with OUTPUT_PATH.open("a", newline="", encoding="utf-8") as file:
        writer = csv.DictWriter(file, fieldnames=FIELDNAMES)
        if not file_exists:
            writer.writeheader()

        for config_name, k in [("k3_baseline", 3), ("k5_context", 5)]:
            for index, item in enumerate(questions, start=1):
                question = item.get("question")
                if not question:
                    print(f"Skipping test case {index}: missing 'question' field")
                    continue

                started = time.perf_counter()
                results = retrieve(question, k=k)
                latency_ms = round((time.perf_counter() - started) * 1000, 2)
                documents = results.get("documents", [[]])[0]
                context = "\n---\n".join(documents)

                writer.writerow({
                    "run_id": run_id,
                    "timestamp": timestamp,
                    "config_name": config_name,
                    "question_id": item.get("id", index),
                    "question": question,
                    "retrieved_k": k,
                    "retrieved_context": context,
                    "answer": "",
                    "recall_at_k": "Not measured",
                    "mrr": "Not measured",
                    "faithfulness": "Not measured",
                    "answer_relevance": "Not measured",
                    "latency_ms": latency_ms,
                    "notes": "Retrieval logged; answer-generation metrics not calculated",
                })

    print(f"Logged results to {OUTPUT_PATH}")
    print(f"Run ID: {run_id}")


if __name__ == "__main__":
    main()
```

### Before running it

1. Inspect `data/eval_set.json` and confirm each question uses the `question` field.
2. Confirm `src.retrieval.retrieve(question, k=k)` matches your function signature.
3. Run from the project root:

```powershell
python -m src.log_eval_results
```

4. Review `data/eval_results.csv` and confirm both configurations were run against the same questions.

If the JSON structure differs, adapt `load_questions()` rather than changing the dataset blindly.

## 5. Inspect and interpret the log

Check whether both configurations ran against the same questions, whether each result has a run ID and question ID, whether latency values look plausible, and whether unavailable metrics are clearly marked. A log records what happened; it does not by itself prove which configuration is better.

## Key takeaways

- A consistent test set makes comparisons more meaningful.
- Log the configuration, question, retrieved context, and available scores.
- Use run IDs and timestamps so results are traceable.
- Mark unavailable metrics honestly instead of guessing.
- Keep evaluation logs reproducible and safe to commit.
