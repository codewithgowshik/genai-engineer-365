# 2. What Is the Hugging Face Hub?

The Hugging Face Hub is an online platform for hosting, sharing and downloading machine learning models, datasets and applications.

Think of it as GitHub for AI models.

Developers can upload trained models so other people can download and use them.

### What can we publish?

1. Machine learning models.
2. Fine-tuned models.
3. LoRA adapters.
4. Datasets.
5. Model documentation.
6. AI applications and demos.

Website: https://huggingface.co/

# 3. Important Concepts

| Concept | Explanation |
|---|---|
| Hugging Face Hub | Platform for hosting AI models and datasets. |
| Repository | Online storage for model files. |
| Model Card | Documentation explaining the model. |
| Access Token | Credential used to authenticate with Hugging Face. |
| Public Repository | Anyone can access the repository. |

A model repository is a folder hosted on Hugging Face.

Example:

```text

```

The repository contains the files required to understand and reuse the published adapter.

# 4. What Are We Uploading?

In our fine-tuning project, we used LoRA.

LoRA stands for Low-Rank Adaptation.

Instead of updating every parameter in the original model, LoRA introduces smaller trainable components called adapters.

After training, we can save and publish these adapter weights separately.

### Base Model vs LoRA Adapter

**Base model:**

The original pretrained model.

Example:

`Qwen/Qwen2.5-0.5B`

**LoRA adapter:**

The additional trained weights that adapt the base model.

The adapter usually does not contain the complete original model.

Therefore, anyone downloading the adapter needs access to the compatible base model as well.

# 5. Hugging Face Authentication

Before uploading a model, we need to authenticate.

Hugging Face uses access tokens to identify users and control permissions.

### Step 1: Create an Access Token

1. Open https://huggingface.co/settings/tokens
2. Log in to your account.
3. Create a new token.
4. Give it permission to create and write to repositories.
5. Copy the token securely.

**Security rule:**

Never publish your access token in GitHub, public notebooks or screenshots.

# 6. Uploading the LoRA Adapter

We can upload a trained PEFT model using:

```python
model.push_to_hub()
```

### Example

```python
from peft import PeftModel

REPO_ID = "YOUR_USERNAME/qwen2.5-lora-finetuned"

model.push_to_hub(
    REPO_ID,
    private=True
)

print("Adapter uploaded successfully!")
```

Replace `YOUR_USERNAME` with your Hugging Face username.

**Important:** The `model` variable must contain the trained PEFT model with the actual trained adapter attached.

This code does not train a model. It uploads an existing trained adapter.

The repository is private in this example.

# 7. Uploading the Tokenizer

A tokenizer converts text into tokens that the model can process.

The tokenizer should be compatible with the base model.

We can upload it separately:

```python
tokenizer.push_to_hub(REPO_ID)

print("Tokenizer uploaded successfully!")
```

Now the adapter and tokenizer files are available in the repository.

# 8. Creating a Model Card

A Model Card explains what the model does and how other developers can use it.

It should include:

- Model name.
- Base model.
- Fine-tuning method.
- Training dataset description.
- Intended use.
- Evaluation results.
- Limitations.
- Usage instructions.

Example:

```markdown
# Qwen2.5 LoRA Fine-Tuned Model

## Overview

This repository contains a LoRA adapter
built on top of Qwen2.5-0.5B.

## Base Model

Qwen/Qwen2.5-0.5B

## Fine-Tuning Method

LoRA (Low-Rank Adaptation)

## Purpose

This project explores parameter-efficient
fine-tuning of an open-source language model.

## Training

The adapter was trained using a small
instruction-following dataset.

## Limitations

This is an educational experiment.
It is not a production-ready model.

## Usage

Load the original base model and attach
the adapter using the PEFT library.
```

Do not claim evaluation improvements unless you have measured them.

# 9. Verifying the Published Adapter

After uploading:

1. Open your Hugging Face profile.
2. Open your model repository.
3. Check that the adapter files exist.
4. Confirm that the repository contains the correct base model information.
5. Check that the repository visibility is correct.

Expected files:

```text
qwen2.5-lora-finetuned/
│
├── adapter_config.json
├── adapter_model.safetensors
├── tokenizer_config.json
├── tokenizer.json
└── README.md
```

The exact tokenizer files may vary.

### Why is verification important?

Uploading files does not automatically prove that the adapter works.

We should verify that the files exist and that the adapter can be loaded with its compatible base model.

# 10. GitHub vs Hugging Face Hub

Both platforms are useful, but they serve different purposes.

| GitHub | Hugging Face Hub |
|---|---|
| Hosts source code | Hosts AI models and datasets |
| Stores Python scripts | Stores model weights |
| Tracks code changes | Tracks model versions |
| Hosts project documentation | Hosts model cards |
| Supports software collaboration | Supports AI model sharing |

### My approach

**GitHub:**
- Python scripts.
- Training configuration.
- Evaluation code.
- README files.
- Project documentation.

**Hugging Face Hub:**
- LoRA adapter weights.
- Adapter configuration.
- Compatible tokenizer files.
- Model card.

Avoid uploading large model weights to an ordinary GitHub repository.

---

# 11. Important Security Considerations

Before publishing an adapter:

1. Never expose access tokens.
2. Never upload private or sensitive training data.
3. Check the base model's licence.
4. Check whether the training dataset can legally be shared.
5. Choose public or private repository visibility carefully.
6. Document the model's limitations.

A public model repository makes your uploaded files accessible to other users.

# 12. LinkedIn Publication

## Fine-Tuning vs Prompting vs RAG: My Mental Model

As I've been learning about LLMs, one question keeps coming up:

When should we use Prompting, RAG or Fine-Tuning?

Here's how I understand the difference.

### 1. Prompt Engineering – Tell the model what to do.

Use it when you want to guide the model's behaviour through instructions without changing its weights.

### 2. RAG – Give the model information.

Use it when the model needs access to external, private or frequently changing knowledge.

The system retrieves relevant information and provides it as context to the LLM.

### 3. Fine-Tuning – Change how the model behaves.

Use it when you want to adapt a pretrained model to a specific task, response style or specialised pattern using additional training.

### My simple decision framework:

- Need better instructions? → Prompting.
- Need external or updated knowledge? → RAG.
- Need consistent specialised behaviour? → Fine-Tuning.

One important lesson I've learned:

Fine-tuning is not automatically better than RAG or prompting. The right approach depends on the problem.
