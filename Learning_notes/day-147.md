## 1. Learn — Demo planning

A useful demo should show the application solving a real problem, not just displaying a chat interface.

Plan a short walkthrough:

1. **Introduce the goal:** Explain that the app answers questions using a supplied knowledge base.
2. **Ask an answerable question:** Choose one whose answer is clearly present in `data/documents.txt`.
3. **Show grounded answering:** Explain how retrieval and reranking select relevant passages before Gemini generates a response.
4. **Show evidence:** Point out the source or citation information available in the current interface.
5. **Test an unanswerable question:** Ask about information absent from the documents and show whether the system acknowledges the limitation.
6. **Explain one improvement:** Use a result from the evaluation suite to describe a quality change.

Only claim features that are implemented and tested. If the UI does not yet display source cards, describe citations only to the extent that they are actually visible or returned by the API.

## 2. Build — Iterate on quality

Use the evaluation results from Day 146 to choose one concrete issue. Avoid changing several components at once; a focused change makes it easier to determine what helped.

### Suggested workflow

1. Run the current tests and record the baseline.
2. Identify a failure or weakness.
3. Make one targeted change.
4. Run the same tests again.
5. Compare results and note whether quality improved or regressed.

### Possible quality improvements

Choose only one that matches an observed problem:

- **Weak retrieval:** Add evaluation questions that reflect real user wording, then inspect whether the correct source appears in the top results.
- **Unsupported answers:** Strengthen the grounding instructions in `src/generation.py` and test questions whose answers are absent from the documents.
- **Missing or unclear citations:** Verify that citation IDs correspond to the retrieved passages and that the UI presents them accurately.
- **Slow responses:** Measure retrieval-plus-reranking latency separately from Gemini generation before optimising.
- **Poor source coverage:** Review the source document and chunking strategy before changing retrieval settings.

Do not assume a change improved quality until the same evaluation cases have been run again.

## 3. Run the evaluation suite

From the project root, run:

```cmd
python -m pytest tests/test_evaluation.py -v -s
```

Record the baseline and updated results. If a test fails, inspect the failure rather than weakening the assertion just to make the suite pass.

The current initial suite checks that retrieval returns passages, checks source/citation metadata, and measures retrieval-plus-reranking latency. It does not by itself establish answer correctness, faithfulness, citation accuracy, or Gemini API cost.

## 4. Prepare the demo

Create a small demo checklist:

- [ ] Backend starts successfully.
- [ ] Frontend starts successfully.
- [ ] An answerable question returns a grounded answer.
- [ ] An unanswerable question is handled without inventing facts.
- [ ] Citations or source information are shown accurately, if implemented.

- [ ] The evaluation suite runs successfully.

Example question categories (adapt them to the actual content of `data/documents.txt`):

- A question answered explicitly in the documents.
- A question that requires combining information from the documents.
- A question whose answer is absent from the documents.

## 5. Commit and push

After reviewing the diff and rerunning tests:

```cmd
git status
git diff
git add src/generation.py src/retrieval.py src/reranking.py tests
git commit -m "Day 147: improve RAG answer quality"
git push
```

Stage only the files you intentionally changed. If the improvement touched a different file, add that file instead. Do not commit `.env`, API keys, `.venv`, `chroma_data`, or `node_modules`.

## Key takeaway

Quality iteration is a measured loop: establish a baseline, identify a real failure, make one focused change, and evaluate again. A polished demo should show both what the RAG application can do and where its evidence or implementation is limited.
