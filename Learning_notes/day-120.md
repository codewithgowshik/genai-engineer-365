# Day 120 — Experiment with Chunk Size and Overlap

## Objective

Today I learned how chunk size and chunk overlap affect the quality of retrieval in a RAG system. I already learned basic chunking in the earlier stages of the project, so today's goal was to go deeper and understand the trade-offs involved in choosing chunking parameters.

The main idea is simple: before a RAG system can retrieve useful information, documents need to be divided into smaller pieces called chunks. The way those chunks are created directly affects what the retriever can find later.

## What Is Chunk Size?

Chunk size determines how much text is included in each chunk. For example, if a chunk size of 100 characters is used, the document is divided into sections containing approximately 100 characters each.

A smaller chunk can make retrieval more specific because it contains less unrelated information. However, if the chunk becomes too small, important context can be separated across multiple chunks.

A larger chunk keeps more information together. This can provide the LLM with more context, but the chunk may also contain information that is not relevant to the user's question.

Therefore, there is a trade-off between specificity and context.

```text
Small chunks
→ More specific information
→ Less surrounding context

Large chunks
→ More surrounding context
→ Potentially more unrelated information
```

There is no single chunk size that is automatically best for every RAG application. The appropriate size depends on the type of documents and the questions users are expected to ask.

## What Is Chunk Overlap?

Chunk overlap means that neighbouring chunks share some of the same text.

Without overlap, chunks can be separated directly at a boundary:

```text
Chunk 1: A B C D E
Chunk 2: F G H I J
```

With overlap, part of the previous chunk is repeated in the next chunk:

```text
Chunk 1: A B C D E
Chunk 2:       D E F G H
Chunk 3:             G H I J K
```

The purpose of overlap is to reduce the chance that important information is lost because it happens to fall across a chunk boundary.

For example, a sentence might be split between two chunks. If the first chunk ends before the sentence is complete, the second chunk contains the remaining words. Overlap allows some surrounding text to appear in both chunks, which can preserve more context.

## How Chunk Size and Overlap Work Together

Chunk size controls how much information is inside each chunk, while overlap controls how much information is shared between neighbouring chunks.

For example:

```text
chunk_size = 100
overlap = 20
```

The next chunk starts 80 characters after the previous chunk started because:

```text
100 - 20 = 80
```

This means the final 20 characters of one chunk can also appear at the beginning of the next chunk.

Conceptually:

```text
Chunk 1
[----------------------------------------]
0                                      100

Chunk 2
                    [----------------------------------------]
                    80                                      180
                    ↑
                  overlap
```

## Example Chunking Function

The chunking function can accept both `chunk_size` and `overlap` as parameters:

```python
def chunk_documents(documents, chunk_size=100, overlap=20):
    chunks = []

    for document in documents:
        start = 0

        while start < len(document):
            end = start + chunk_size
            chunk = document[start:end]
            chunks.append(chunk)
            start += chunk_size - overlap

    return chunks
```

The important part is:

```python
start += chunk_size - overlap
```

This determines where the next chunk begins.

## What Should I Compare?

The goal is not simply to find which configuration produces the most chunks. I need to examine the quality of the retrieved information.

For each configuration, I should ask whether the correct information was retrieved, whether the retrieved chunk contains enough context, whether the chunk contains too much unrelated information, and whether overlap helps preserve important information between neighbouring chunks.

A useful experiment table is:

| Chunk Size | Overlap | Observation |
|---:|---:|---|
| 50 | 0 | Very small chunks and limited context |
| 100 | 0 | Baseline configuration |
| 100 | 20 | More shared context between chunks |
| 200 | 40 | Larger chunks with more overlap |

The observations should come from the actual results produced by the dataset rather than assuming that one configuration is always better.

This shows why chunking is important. Chunking happens before embeddings and retrieval, but its effects are visible later when the system searches for relevant information.

If the chunks are poorly designed, the retriever may return incomplete or irrelevant information. This can then affect the quality of the final grounded answer.

## Important Lesson

Chunking is not just a preprocessing step that can be ignored. It is part of retrieval quality.

A good RAG system needs to balance the amount of information inside each chunk with the amount of context shared between chunks.

The experiment also showed why it is better to test different configurations rather than assuming a fixed chunk size and overlap will work for every dataset.
