# 2. What Is Inference?

Inference is the process of using a trained machine learning model to generate predictions or responses based on new input data.

For example:

When a user asks an LLM:

"What is Artificial Intelligence?"

The model:

1. Receives the input prompt.
2. Converts the input into tokens.
3. Processes the tokens.
4. Generates output tokens.
5. Returns the final response.

This process is called inference.

### Training vs Inference

| Training | Inference |
|---|---|
| Teaches a model using data. | Uses an already-trained model. |
| Updates model parameters. | Uses existing model parameters. |
| Requires substantial computational resources. | Resource requirements depend on the model and workload. |
| Happens during model development. | Happens whenever users interact with the model. |

**Key takeaway:** Training teaches the model, while inference allows applications to use the model.

# 3. What Is an Inference Server?

An inference server is software that makes machine learning models available to applications through an interface, commonly an API.

It handles:

- Loading models into memory.
- Receiving inference requests.
- Processing prompts.
- Generating model responses.
- Returning responses to applications.
- Managing concurrent requests.

### Example Architecture

```text
          User
            |
            v
      React Frontend
            |
            v
      Node.js Backend
            |
            v
      Inference Server
            |
            v
         LLM Model
            |
            v
      Generated Response
            |
            v
       User Interface
```

### Why Do We Need Inference Servers?

Imagine building an AI-powered application with 1,000 users.

Every user might send multiple requests to the language model.

An inference server manages these requests and provides an efficient way to serve model responses.

Without an appropriate serving system, managing multiple users and requests can become difficult.

# 4. Introduction to vLLM

vLLM is an open-source inference and serving engine designed for efficient Large Language Model serving.

It helps developers deploy and serve LLMs with high throughput and efficient GPU memory management.

Official documentation:

https://docs.vllm.ai/

### Important Features of vLLM

#### 4.1 High Throughput

Throughput measures how much work a system processes over a given period.

For LLMs, it can be measured using:

- Tokens per second.
- Requests per second.

Higher throughput means the system can process more work within the same amount of time.

#### 4.2 Low Latency

Latency measures the time taken to process a request and return a response.

Lower latency generally means users receive responses faster.

#### 4.3 Continuous Batching

Continuous batching dynamically schedules requests so that multiple requests can share GPU execution efficiently.

Instead of waiting for an entire batch to finish before admitting new requests, the system can continuously manage incoming requests.

#### 4.4 PagedAttention

PagedAttention is a memory management technique used by vLLM.

It manages the Key-Value (KV) cache in memory blocks, helping reduce memory fragmentation and improve memory utilisation.

### Why Is vLLM Important?

Consider an AI application with hundreds of simultaneous users.

A serving engine must efficiently manage:

- GPU memory.
- Incoming requests.
- Token generation.
- Concurrent users.
- Computational resources.

vLLM provides specialised mechanisms to improve LLM serving performance.

**Important:** vLLM is an inference and serving engine, not a model itself.

# 5. Understanding LLM Latency

Latency is the time taken by a system to respond to a request.

In LLM applications, latency directly affects the user experience.

For example:

A user asks a question.

- Model A responds in 1.5 seconds.
- Model B responds in 5 seconds.

Model A has lower total response latency for this particular request.

However, response quality must also be considered.

### 5.1 Time to First Token (TTFT)

TTFT measures how long it takes from sending a request until receiving the first generated token.

Example:

```text
Request sent:       10:00:00
First token arrives: 10:00:01

TTFT = 1 second
```

Lower TTFT means users see the beginning of the response sooner.

### 5.2 Total Response Latency

Total response latency measures the time between submitting a request and receiving the complete response.

Example:

```text
Request sent:       10:00:00
Response completed: 10:00:04

Total latency = 4 seconds
```

### 5.3 Tokens Per Second (TPS)

Tokens per second measures how quickly the model generates output tokens.

Formula:

```text
TPS = Generated Tokens / Generation Time
```

Example:

```text
Generated tokens = 100
Generation time = 5 seconds

TPS = 100 / 5

TPS = 20 tokens per second
```

Higher TPS generally means faster token generation.

### 5.4 Average Latency

A single benchmark is not sufficient to evaluate model performance.

We should repeat the same test multiple times.

Example:

| Test | Latency |
|---|---:|
| Test 1 | 2 seconds |
| Test 2 | 2.5 seconds |
| Test 3 | 3 seconds |
| Test 4 | 2 seconds |
| Test 5 | 2.5 seconds |

Formula:

```text
Average Latency = Sum of All Latencies / Number of Tests
```

Calculation:

```text
(2 + 2.5 + 3 + 2 + 2.5) / 5

Average = 2.4 seconds
```

# 6. Understanding Latency vs Throughput

These two measurements are related but different.

| Latency | Throughput |
|---|---|
| Measures response time. | Measures processing capacity. |
| Focuses on how long a request takes. | Focuses on how much work is completed. |
| Lower is generally better. | Higher is generally better. |
| Example: 2 seconds per response. | Example: 500 tokens per second across a workload. |

An inference server can have high throughput while individual requests still experience noticeable latency.

Both measurements are important when evaluating production AI systems.

# 7. What Is Ollama?

Ollama is a tool that allows developers to run and manage language models locally.

Website:

https://ollama.com/

It provides:

- Local model execution.
- Model downloading.
- Model management.
- An HTTP API.
- Support for different open models.

For today's practical work, Ollama acts as our local model runtime and API provider.

### Useful Commands

Download a model:

```bash
ollama pull llama3.2:1b
```

Download another model:

```bash
ollama pull llama3.2:3b
```

List installed models:

```bash
ollama list
```

Run a model:

```bash
ollama run llama3.2:1b
```

# 8. How Model Benchmarking Works

Benchmarking means measuring the performance of a system using a defined test.

For local LLM benchmarking, we can measure:

1. Total response latency.
2. Time to first token.
3. Generated tokens.
4. Tokens per second.
5. Average latency.
6. Performance differences between models.

### Example Model Comparison

| Metric | Model A (1B) | Model B (3B) |
|---|---:|---:|
| Average latency | 1.2 seconds | 2.5 seconds |
| Tokens generated | 100 | 100 |
| Tokens per second | 45 | 25 |
| Model size | Smaller | Larger |

*Illustrative values only. Actual results depend on hardware, model configuration and workload.*

### Why Can Smaller Models Be Faster?

Smaller models generally require:

- Less memory.
- Fewer computational operations.
- Less GPU or CPU processing capacity.

However, larger models may provide better responses on certain tasks.

The best model depends on the application's requirements.

# 9. Important Benchmarking Considerations

A reliable benchmark should control the testing environment.

Consider the following:

### 9.1 Hardware

Performance depends on:

- CPU.
- GPU.
- Available VRAM.
- System RAM.
- Storage speed.

### 9.2 Model Size

Larger models generally require more computational resources.

### 9.3 Quantization

Quantization reduces the numerical precision used to represent model weights.

It can reduce memory requirements and sometimes improve inference speed.

However, quantization may affect model quality.

### 9.4 Warm-Up Requests

The first request may take longer because the model needs to load into memory.

A warm-up request helps reduce this initial loading effect when measuring subsequent requests.

### 9.5 Multiple Runs

Run each benchmark several times.

Calculate the average rather than relying on a single result.

### 9.6 Consistent Prompts

Use the same prompts and generation settings when comparing models.

Otherwise, the comparison may not be fair.
