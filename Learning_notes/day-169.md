# 2. What Is Training Configuration?

Training configuration means defining the settings that control how an AI model learns.

Before training an AI model, we need to decide:

- How quickly should the model learn?
- How many examples should it process at once?
- How many times should it study the dataset?
- How should the model update its parameters?
- How much memory can it use?

These settings are called **hyperparameters**.

Example:

```python
learning_rate = 0.0002
batch_size = 1
num_train_epochs = 3
gradient_accumulation_steps = 4
```

These values control different parts of the training process.

# 3. Important Training Hyperparameters

## 3.1 Learning Rate

Learning rate controls how much the model's trainable parameters change during each optimisation update.

Think of it like learning something new.

- Very high learning rate: You may make excessively large adjustments.
- Very low learning rate: Learning may take too long.
- Appropriate learning rate: More controlled learning.

Example:

```python
learning_rate = 2e-4
```

`2e-4` means:

```text
0.0002
```

This is a common starting point for LoRA experiments, not a universal best value.

## 3.2 Batch Size

Batch size means how many training examples the model processes in one training step.

Example:

```python
per_device_train_batch_size = 1
```

This means the model processes one example per device in each batch.

Why use a small batch size?

- Reduces GPU memory requirements.
- Helps when working with limited hardware.
- Makes small-scale experiments easier.

## 3.3 Epochs

An epoch means one complete pass through the training dataset.

Example:

```python
num_train_epochs = 3
```

This means the model goes through the entire training dataset three times.

For example, if the dataset contains 100 examples:

- Epoch 1: Processes all 100 examples.
- Epoch 2: Processes all 100 examples again.
- Epoch 3: Processes all 100 examples again.

Too many epochs can cause overfitting.

**Overfitting:** When a model performs well on its training examples but struggles with new, unseen examples.

## 3.4 Gradient Accumulation

Gradient accumulation allows the model to combine gradients from multiple smaller batches before updating its parameters.

Example:

```python
gradient_accumulation_steps = 4
```

Suppose:

```text
Batch size = 1
Gradient accumulation = 4
Number of GPUs = 1
```

Effective batch size:

```text
1 × 4 × 1 = 4
```

The model processes four examples across four forward/backward passes before an optimiser update.

This helps simulate a larger batch without requiring all examples to fit into GPU memory simultaneously.

## 3.5 Optimiser

An optimiser updates the trainable parameters based on the calculated gradients.

A commonly used optimiser is AdamW.

It helps determine how the model adjusts its parameters during training.

# 6. Understanding the Important Library Terms

This is one of the most important parts of today's lesson.

## 6.1 Transformers Library

Transformers is a Hugging Face library used to load and work with pretrained models.

### AutoTokenizer

```python
from transformers import AutoTokenizer
```

A tokenizer converts text into tokens and token IDs that a language model can process.

For example:

```text
Input: Hello, how are you?
```

The tokenizer converts the text into token IDs.

Why do we need it?

Language models do not directly process ordinary text. They process numerical representations of tokens.

### AutoModelForCausalLM

```python
from transformers import AutoModelForCausalLM
```

This loads a pretrained causal language model.

Causal language models generate text by predicting the next token based on previous tokens.

Examples include the Qwen and Llama model families.

### BitsAndBytesConfig

```python
from transformers import BitsAndBytesConfig
```

This configures quantisation options when loading supported models.

For example:

```python
BitsAndBytesConfig(
    load_in_4bit=True
)
```

This tells the model-loading process to load the model's weights in 4-bit representation.

Why?

To reduce GPU memory requirements.

## 6.2 PEFT Library

PEFT stands for **Parameter-Efficient Fine-Tuning**.

It provides techniques that adapt pretrained models without updating all their original parameters.

### LoraConfig

```python
from peft import LoraConfig
```

This defines the LoRA configuration.

Example:

```python
lora_config = LoraConfig(
    r=8,
    lora_alpha=16,
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"]
)
```

Understanding the settings:

| Parameter | Meaning |
|---|---|
| `r` | Rank of the LoRA matrices |
| `lora_alpha` | Scaling factor for LoRA updates |
| `lora_dropout` | Dropout applied to LoRA inputs during training |
| `target_modules` | Model layers where LoRA adapters are added |

### prepare_model_for_kbit_training

```python
from peft import prepare_model_for_kbit_training
```

This prepares a quantised model for parameter-efficient training.

It applies the necessary preparation steps for supported low-bit training workflows.

### get_peft_model

```python
from peft import get_peft_model
```

This applies the PEFT configuration to the pretrained model.

For example:

```python
model = get_peft_model(model, lora_config)
```

This attaches the LoRA adapters to the model.

It does not train the adapters yet.

### print_trainable_parameters

```python
model.print_trainable_parameters()
```

This displays how many parameters can be trained compared with the total number of parameters.

It helps us understand how parameter-efficient fine-tuning reduces the number of trainable parameters.

## 6.3 Datasets Library

The Datasets library helps us create, load, process and manage training datasets.

### Dataset.from_dict()

```python
from datasets import Dataset

dataset = Dataset.from_dict(data)
```

This converts a Python dictionary into a Hugging Face Dataset object.

For example:

```python
data = {
    "instruction": ["What is Python?"],
    "output": ["Python is a programming language."]
}
```

The library converts this into a dataset that can be used in our training pipeline.

## 6.4 TRL Library

TRL stands for Transformer Reinforcement Learning.

It provides tools for training and fine-tuning language models.

For our project, we use its supervised fine-tuning functionality.

### SFTTrainer

```python
from trl import SFTTrainer
```

SFTTrainer is a trainer designed for supervised fine-tuning.

It coordinates the training process using:

- A model.
- A training dataset.
- A tokenizer or processing class.
- Training arguments.

### SFTConfig

```python
from trl import SFTConfig
```

SFTConfig defines settings for supervised fine-tuning.

Example:

```python
training_config = SFTConfig(
    output_dir="./output",
    learning_rate=2e-4,
    num_train_epochs=3
)
```

This defines where training outputs are saved and how training should run.

## 6.5 Accelerate Library

Accelerate helps manage model execution across available hardware.

It simplifies running training workloads on GPUs and supported multi-device environments.

## 6.6 bitsandbytes Library

bitsandbytes provides memory-efficient operations for supported models.

We use it in our project because it supports 4-bit quantisation.

This is particularly useful when working with limited GPU memory.

Our Day 169 project follows this sequence:

```text

     |

     |

```

Let's understand each stage.

### Stage 1: Connect GPU

We use the GPU to accelerate model operations.

### Stage 2: Install Libraries

We install the libraries required for model loading, dataset preparation and training.

### Stage 3: Create Dataset

We prepare instruction-and-response examples.

Example:

```json
{
  "instruction": "What is Python?",
  "output": "Python is a programming language."
}
```

### Stage 4: Load Pretrained Model

We download an existing language model.

Our experiment uses:

`Qwen/Qwen2.5-0.5B`

This is a base model, not the instruction-tuned variant.

### Stage 5: Configure Quantisation

We configure 4-bit quantisation to reduce model memory requirements.

This makes our experiment a QLoRA workflow rather than ordinary full-precision LoRA.

### Stage 6: Configure LoRA

We define the rank, scaling factor, dropout and target modules.

### Stage 7: Attach LoRA Adapters

We use `get_peft_model()` to attach trainable adapters to the model.

### Stage 8: Configure Training

We define the learning rate, batch size, epochs and other settings.

### Stage 9: Launch Training

We use:

```python
trainer.train()
```

This starts the supervised fine-tuning process.

The trainer processes the training data, calculates losses and updates the trainable parameters.

### Stage 10: Save the Adapter

We save the trained LoRA adapter.

Example:

```python
model.save_pretrained("./day169-lora-adapter")
```

This saves the adapter weights and configuration.

It does not save a complete independent copy of the original pretrained model.

# 8. LoRA vs QLoRA

| Feature | LoRA | QLoRA |
|---|---|---|
| Full name | Low-Rank Adaptation | Quantized Low-Rank Adaptation |
| Base model | Usually loaded in its normal supported precision | Loaded in quantised form |
| Adapters | Trainable | Trainable |
| Base weights | Usually frozen | Frozen |
| Memory usage | Lower than full fine-tuning | Further reduced through quantisation |
| Main purpose | Efficient model adaptation | Memory-efficient model adaptation |

**Important:** Our Day 169 experiment uses 4-bit quantisation together with LoRA adapters. Therefore, it is a QLoRA experiment.

# 9. Important Training Concepts

## Overfitting

When a model memorises training examples but performs poorly on unseen data.

## Underfitting

When a model has not learned the intended patterns sufficiently.

## Training Loss

A measurement of how far the model's predictions are from the expected targets during training.

Lower training loss does not automatically mean better real-world performance.

## Validation Dataset

A separate dataset used to monitor model performance during development.

## Test Dataset

A separate dataset used for final evaluation.

The test dataset should not be used to train the model.

# 10. Important Technical Distinction

Our five-example demonstration dataset is only a pipeline test.

It can help us verify that:

- The dataset can be created.
- The model can be loaded.
- LoRA can be configured.
- The training pipeline can run.
- An adapter can be saved.

It is not enough to produce a useful, general-purpose fine-tuned model.

For a meaningful experiment, we need a larger, diverse and quality-checked dataset.

We should also preserve the evaluation examples from Day 167 and Day 168 so they remain unseen during training.
