## Learning objective

Understand how to compare local language models using the same prompts and testing conditions. Evaluate their response quality, speed, token generation rate, and memory usage.

## 1. Small vs. large language models

A language model contains learned numerical values called **parameters**. These parameters help the model recognise patterns and generate responses.

- **3B** means approximately 3 billion parameters.
- **9B** means approximately 9 billion parameters.

A model with more parameters may have greater capacity, but it is not automatically better at every task. Performance also depends on its architecture, training data, quantisation, and the task being tested.

| Aspect | Smaller model | Larger model |
|---|---|---|
| Memory requirement | Usually lower | Usually higher |
| Inference speed | Often faster | Often slower |
| Hardware requirement | Usually lower | Usually higher |
| Task performance | Can be capable, but may struggle with some tasks | May perform better on some complex tasks |

These are general tendencies, not guarantees.

## 2. What is model benchmarking?

**Benchmarking** is the process of testing models under consistent conditions and measuring their performance.

For a fair practical comparison:
1. Give each model the same prompts.
2. Use the same generation settings, such as temperature.
3. Run the models one at a time.
4. Separate the first model-loading run from later responses.
5. Record the measurements and inspect the answers.

A comparison between different model families or generations is useful for choosing a practical model, but it does not isolate model size as the only cause of a performance difference.

## 3. Important comparison metrics

### Response quality
How accurate, relevant, complete, and clear is the answer? Quality should be judged against the task, not simply by answer length.

### Response time
The total time taken to produce a response. The first request may take longer because Ollama needs to load the model.

### Tokens per second
A measure of how quickly the model generates output tokens.

**Calculation:**

`tokens per second = generated token count / generation time in seconds`

Ollama's chat API can return:
- `eval_count`: number of generated tokens
- `eval_duration`: time spent generating those tokens, in nanoseconds

Convert nanoseconds to seconds by dividing by 1,000,000,000.

### Memory usage
The RAM and/or GPU memory used while the model is loaded and generating responses. Larger models generally require more memory, but quantisation and runtime settings also affect usage.

### Reasoning performance
How well the model handles tasks that require multiple steps, such as explaining a concept, solving a problem, or following instructions.

## 4. What is inference?

**Inference** is the process of using a trained model to generate an output from an input prompt.

In this project:
1. Python sends a prompt to Ollama.
2. Ollama passes the prompt to the selected local model.
3. The model generates a response.
4. Ollama returns the response and timing information to Python.
5. Python records the results for comparison.

## 5. Ollama and its local API

Ollama runs language models locally and provides an HTTP API that Python can call.

Default local API address:

`http://localhost:11434`

Chat endpoint:

`POST http://localhost:11434/api/chat`

A request includes:
- `model`: the model name to run
- `messages`: the conversation messages
- `stream`: set to `false` to receive the complete response in one result

The Ollama server must be running before Python can send requests.

Useful commands:

```powershell
ollama list
ollama pull qwen2.5:3b
ollama run qwen2.5:3b
ollama run qwen3.5:9b
ollama ps
```

## 6. Today's practical model comparison

Models selected:

| Role | Model |
|---|---|
| Smaller model | `qwen2.5:3b` |
| Larger model | `qwen3.5:9b` |

These are from different model generations, so this experiment compares their practical performance; it is not a controlled test of parameter count alone.

### Experiment procedure

1. Confirm both models are available with `ollama list`.
2. Send the same set of prompts to each model.
3. Use the same generation settings for both.
4. Run one model at a time to avoid competing for system resources.
5. Run a warm-up request for each model.
6. Record response time, generated token count, tokens per second, and memory usage.
7. Review the answers for accuracy, relevance, completeness, and clarity.
8. Save the results in a comparison report.

### Suggested test prompts

1. **Explanation:** Explain how an API works to a beginner using a simple example.
2. **Reasoning:** A shop sells an item for £80 after a 20% discount. What was its original price? Explain the calculation.
3. **Coding:** Write a simple Python function that checks whether a number is even, and explain it.

Use exactly the same wording for both models.

## 7. Key takeaways

- Model size is one factor that can affect capability and resource use.
- A larger model is not automatically the best choice.
- Benchmarking requires consistent prompts and settings.
- Response time and tokens per second measure different aspects of speed.
- The first request may include model-loading time.
- Answer quality needs to be evaluated, not assumed from model size.
- Local inference allows models to run on your own computer through tools such as Ollama.
